### 2.11 语音输入的交互修正与四个实测缺陷（v1.4）

**起因**：用户实测后一句「语音输入，你是不是没有连接文本框？问了也没用」。
复盘确认：识别成功后直接出卡，界面上看不到识别文本 —— 老人无法核对，识别错一个词就直接给错误指导。

**四个缺陷全部有日志证据（不是推测）**：

| # | 日志原文 | 根因 |
|---|---|---|
| 1 | `already-recording` ×13 | 两个按钮各挂一个 window 的 `pointerup`，一次松手触发两次；`pointerdown` 与 `keydown` 也各触发一次 |
| 2 | `音频 26026ms` / `音频 52394ms`（上限 15s） | 重复 start 使旧 MediaStream 未关，多个 `onaudioprocess` 同写一个 `chunks`；连朗读声也被录回（`echoCancellation:false`） |
| 3 | `录音达到上限，自动停止` ×3 之后无任何后续日志 | `MAX_MS` 自己调 `stop()`，Promise 结果无人接收 |
| 4 | `SecurityError` ×4 | 页面被嵌在 iframe（WorkBuddy 预览面板），未授予 `microphone` 权限 |

**测试自身的一次失败（这一条比修 bug 更值得记）**：

初版断言是 `ok(/fillInput\(input,\s*r\.text\)/.test(src))` —— 查源码里有没有这串字符。
投毒把它改成 `if (false && fillInput(input, r.text))`，**测试仍然全绿**：字符串还在。

> **文本匹配不是行为断言。** 判据必须能失败，而「源码里有这个字符串」在功能被禁用时依然成立。

改为真驱动流程后（伪造录音态 → 调 `onTalkUp` → 检查 `input.value` 与两个答案区）：

```
投毒：识别完不填框，直接出卡
  ✗ 识别结果应写进日常输入框，实际「」
  ✗ 识别后不应直接出卡（要等用户点提问），实际 daily 0 字符 / emg 273 字符
  ✗ 识别后不应触发紧急模式切换（那是用户点提问后的事）
断言 522 条：通过 519，失败 3
```

注意第三条证据「emg 273 字符」——「煤气漏了怎么办」含危险词，一旦走 `handleQuery` 会切紧急模式并渲染到 `emgAnswer`。只查 `dailyAnswer` 会漏过，这就是为什么两个答案区都要查。

**三次投毒结果**：

| 投毒动作 | 结果 |
|---|---|
| 识别完不填框、直接出卡 | 3 条变红 ✓ |
| 给按钮再挂一个 window pointerup | 1 条变红（「应只挂 1 次，实际 2 次」）✓ |
| `fillInput` 内部不写 `input.value` | 2 条变红 ✓ |

**两处测试自身缺陷（顺带修掉）**：
1. 投毒后脚本崩溃而非干净失败（走了 `fetch`，沙箱无网络）。已在该断言内先 `LLM.configure({enabled:false})`，让降级路径不依赖网络。
2. `e2e_asr.mjs` 原为「识别 → 直接 handleQuery」，跳过了填框，**测的是不存在的产品行为**。已改为「填框 → 检查输入框内容 → 再提问」两步（13 → 19 条断言）。


### 2.12 语音输入改为一步到位（v1.5，用户裁决）

**用户原话**：「把他做成输入后直接出答案，不需要再确认」。

| 轮次 | 识别后行为 | 用户反馈 | 结论 |
|---|---|---|---|
| v1.8 | 直接 `handleQuery` | 「你是不是没有连接文本框？问了也没用」 | 看不到自己说了什么 |

**这里有个容易做错的地方**：反转判据时不能只把 `assert(x===0)` 改成 `assert(x>0)` 就完事。
