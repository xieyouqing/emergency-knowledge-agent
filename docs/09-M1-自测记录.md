### 2.10 模型漂移：一条断言的性质变了（v1.3 记录）

`e2e_llm.mjs` 里「电梯多久年检一次」原本是「置信度门槛的已知代价」的活证据：

| 日期 | confidence | 结果 |
|---|---|---|
| 2026-11-18 | **0.55**（< 0.60 门槛） | 拒答（refuse） |
| 2026-11-19 | **0.72** | 日常卡（daily） |

**排查过程（不是猜）**：
1. `git stash` 掉当日全部改动（`app/app.js`、`app/llm.js`）后重跑 → **仍为 daily**，证明与本次改动无关；
2. 直接问代理 → `{"intent":"prevention","scene":"elevator_trapped","confidence":0.72,"cached":true}`；
3. 100 条评测集重跑 → 四项门槛**仍全过**（98/98/0/0，综合 98.0%）。

**原结论（2026-11-19 早）**：判定这是「跨天的模型版本漂移」，理由是「`temperature:0` 下同一句连调 5 次结果稳定」。

### 2.10.1 修正：原结论错了，不是漂移而是**单次调用抖动**（2026-11-19 晚）

同一句话、同一时刻、`temperature:0`、绕过缓存，**连测 8 次**：

```
0.55 / 0.72 / 0.55 / 0.55 / 0.55 / 0.55 / 0.72 / 0.72
```

| 事实 | 数据 |
|---|---|
| 抖动存在，且就在单次调用层面 | 8 次里 5 次 0.55、3 次 0.72 |
| 抖的是两个**离散值**，不是连续分布 | 只有 0.55 与 0.72 两种取值 → 像被路由到不同推理实例 |
| 门槛 0.60 正好卡在两者之间 | 0.55 → refuse；0.72 → daily |
| 场景判断是稳的 | 8/8 都是 `elevator_trapped` + `prevention`，只有 confidence 在跳 |

**因此「落点是 refuse 还是 daily」在单次调用层面就是随机的**，不是跨天的模型变化。
原文「连调 5 次结果稳定」要么当时恰好落在同一侧，要么样本太少——**5 次不够，这次 8 次才看出来**。

**这条错误的教训比错误本身重要**：

| # | 教训 |
|---|---|
| 1 | 「同一句调 5 次一致」不足以证明无抖动。抖动若是离散二值，5 次全落一侧的概率是 (5/8)^5 ≈ 9.5%，不低 |
| 2 | 判断「是本地随机还是上游波动」，比「换日期复跑」更直接的证据是**同一时刻连续多次调用** |
| 3 | 门槛阈值落在抖动区间内时，**任何基于单次结果的判据都不可靠**——包括「④ 库外误纳率 = 0」 |

**对判据设计的影响**（比修一条测试更重要）：

`MIN_CONFIDENCE = 0.60` 对「真值 confidence 在 0.5–0.75 之间」的样本不稳定。
这类样本的正确处理不是调阈值，而是**改判据形状**：
不再断言「必须落 refuse」或「必须落 daily」，而断言「**落在安全集合内，且绝不能给急救步骤**」。
`e2e_llm.mjs` 已按此改（`expect` 支持 `refuse|daily` 多选 + 额外一条「绝不能是 steps」）。

**已定纪律**（`03` v1.7 已写）：LLM 基线必须带测量日期；复跑前清缓存（`tools/eval/run_eval.mjs` 连的是代理缓存）；每次结果记入本文。

**三次实测记录（同一份 cases.json、同一份代码）**：

| 日期 | 综合 | 备注 |
|---|---|---|
| 2026-11-18 | 97/100 | `03` v1.5 记录 |
| 2026-11-19（早） | 96/100 | `03` v1.7 发现并记录 |
| 2026-11-19（本次） | **98/100** | 本条记录 |

> ⚠️ 三个数字都在「≥96」门槛附近波动。**这个门槛卡在噪声边缘**——意味着单次跑分不能当作能力结论，须看多次的区间。
>
> **2026-11-19 晚补**：这个波动现在有了更准确的解释。不只是「模型版本变了」，
> 而是**单次调用本身就在抖**（§2.10.1，8 次实测 0.55/0.72 交替）。
> 因此 `run_eval.mjs` 的单次成绩只能当「这一次的抽样」，不能当基线；
> 要下结论必须多次跑并看区间。

### 2.17 TTS 引擎注册表与宿主注入（v2.1，docs/11 选项 A）

**这不是重构，是修一个 M3 会咬人的真 bug，顺手把引擎判定收口。**

#### 缺陷本身（静态 + 断言双重确认）

`detect()` 判 tauri 可用性读的是 `global.__TTsProbe`，而唯一注入入口 `setTauriAdapter()` 只写
`__TTsSpeak` / `__TTsStop`。全仓 grep：

```
$ grep -rn "__TTsProbe" app/
app/voice.js:108:  if (typeof global.__TTsProbe === 'function') return Promise.resolve(global.__TTsProbe());
（1 处读，0 处写）
```

后果链条：宿主注入实现 → `detect()` 探针拿不到 → `engine` 停在 `'web'` → `speakTauri` 永不调用
→ Android 浏览器无 `speechSynthesis` → 最终 `engine='none'`，**老人没有声音**。
而语音输出是 `01` §2.1 定的主输出通道。

**M2 一切正常，因为浏览器环境根本不进 tauri 分支**——这就是它一直没被发现的原因。

#### 改法（两条缺一不可）

| # | 改法 | 只做一条会怎样 |
|---|---|---|
| 1 | `setTauriAdapter` 补写 `__TTsProbe`（宿主自带则不覆盖） | 只做这条：页面加载时 `detect()` 已把 engine 定成 web，注入后仍不生效 |
| 2 | 注入后若当前不是 tauri，**重新探测一次** | 只做这条：探针没写，重探也探不出来 |

#### 三次投毒（分别红 2 / 1 / 3 条）

```
投毒A：删掉 __TTsProbe 写入（回到修复前）
  ✗ setTauriAdapter 必须写 __TTsProbe —— 否则 detect() 判不出 tauri（本次修的 bug）
  ✗ 注入适配器后引擎应切到 tauri，实际 web（若为 web 说明注入被静默忽略）

投毒B：写探针但不重探
  ✗ 注入适配器后引擎应切到 tauri，实际 web

投毒C：stop() 不查表
  ✗ engine=tauri 时 stop 应调宿主实现 1 次，实际 0
  ✗ engine=tauri 时 stop 不应调浏览器 cancel，实际 1 次
  ✗ engine=web 时 stop 应调浏览器 cancel 1 次，实际 2
```

> 投毒 A 与 B 红的**不是同一条**，说明两条断言各管一件事：
> A 卡「探针没写」，B 卡「写了但没生效」。只留一条会漏掉另一半。

#### 一个必须知道的观察：断言数会随行为变化

| 状态 | 断言总数 |
|---|---|
| 正常 | 623 |
| 投毒 A | 619（少 4 条） |

原因：部分断言在「引擎是否切到 tauri」的 `if` 分支里，条件不成立就整段跳过。
**看到断言数变少本身是信号**——应想到「有分支没进去」，而不是「测试少跑了」。
没改成「跳过也报红」是因为那会把「引擎本来就是 web」的正常场景误判成失败。

#### 顺带修的第三件（提案里没有）

`stop()` 改成查表后，若 `engine === 'none'` 就没有实现可调 —— 会变成「按了停止什么都不做」。
保留了兜底：没有当前引擎时仍尝试 `speechSynthesis.cancel()` 一次，避免残留合成器继续念。

#### 一个自己写坏的断言（记下来）

第一版断言写成 `ok(W.__TTsProbe !== savedProbe2 ? customCalled >= 0 : true, '（占位）')`。
`customCalled >= 0` **恒为真**，整条断言永远通过——是假断言。已删除。
这类「占位断言」比没有断言更糟：它让人以为覆盖了。
