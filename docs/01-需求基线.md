## 1. 一句话定位

**一个可离线运行的应急知识助手，分日常与紧急两条通道：日常可以问答解释，紧急只给不会出错的步骤。**

### 1.1 双模式（v0.2 核心结构）

| 模式 | 用户状态 | 系统行为 | LLM 权限 |
|---|---|---|---|
| **日常模式** | 不着急，想知道「为什么」「平时怎么防」 | 检索知识库 + 允许 LLM 组织语言、举例、解释原理 | **可改写、可补充解释，不可新增操作步骤** |
| **紧急模式** | 正在出事，注意力 < 10 秒 | 只输出三段式步骤卡，语音优先 | **只选择、排序、精简，禁止生成任何新句子** |

两种模式**共用同一份知识库**（`knowledge/*.json`），差别只在「允许 LLM 做多少」和「输出格式」。

### 1.3 技术形态（v0.3 定稿）

**Tauri 2，一份前端代码产出三个产物。**

| 产物 | 用途 | 离线 | 语音 |
|---|---|---|---|
| **Windows 桌面版**（主演示） | 演示机预装，零安装成本 | 完整 | 系统 SAPI 离线 TTS（Kangkang / Huihui / Yaoyao） |
| **Android APK**（辅证） | 证明移动端可离线 | 完整 | 原生 `TextToSpeech`，需检查中文包可用性 |
| **网页版**（在线降级入口） | 扫码即用，无需安装 | 受限（见 §6.2） | 云 ASR + TTS |

**选择依据（引用）**：Tauri 2.0 于 2024-10-02 发布稳定版，官方原文「Build your app for Linux, macOS, Windows, Android and iOS - **all from a single codebase**」〔D9〕。

**三个产物不冲突的原因**：Tauri 前端就是 web 技术栈，网页版是同一份代码的直接部署，成本接近于零。**"改成软件形态"不等于放弃"发个链接就能看"。**

**已知矛盾（不回避）**：APK 与「老人零门槛」冲突——老人不会装 APK，也不会开未知来源。因此**主演示走桌面版**，APK 只作能力证明。

### 1.4 它不是什么（每条对应一个明确拒绝理由）

| 排除项 | 理由 |
|---|---|
| 通用问答机器人 | 允许自由生成 = 允许编造步骤，应急场景等于致伤风险 |
| 灾情播报 / 新闻资讯 | 灾时用户要的是「我现在该做什么」，不是「发生了什么」 |
| 医疗诊断工具 | 超出能力边界，涉法涉责，一律引导至 120 |
| 事后复盘 / 演练教学 | 主用户群在事发时注意力 < 10 秒，无学习动机 |
| 开放闲聊 | 见 §4.2 边界：只答应急知识与安全常识，不做陪伴型对话 |

## 2. 用户基线

> **重要（v0.2 变更）**：用户群体的**排序没变**（老人 + 低知识人群为主），但**「主链路」从「功能范围」改为「里程碑」**。
> M1 只有文字问答，对老人不可用，**M1 交付物不算主链路跑通**；M2 加上语音，才构成对主用户群的验收。详见 §4.0。

### 2.1 主链路用户（P0 · 最终验收对象 = M2）

**定义：60 岁以上老年人，以及识字量低、无拼音输入能力、不熟悉智能手机操作的人群。**

| 特征 | 数据依据 | 对设计的强制约束 |
|---|---|---|
| 不读长文，注意力极短 | 应急场景通用假设（`推断`，需自测 V3/V5） | 紧急模式首屏只放一个按钮，不复述问题、不寒暄 |
| 不会拼音、不打字 | 非网民中 20.9% 因「不懂拼音等文化程度限制」不上网 〔D5〕 | **紧急模式全程零文字输入**；M1 的文字输入是技术中间态，不是终态 |
| 相当比例不使用互联网 | 60 岁以上占非网民 46.8%，推算约 1.41 亿 〔D5〕`推断` | 不依赖账号、不依赖 App 安装、不依赖历史记录 |
| 是家庭事故的主要受害群体 | 家庭火灾亡人中 60 岁以上占 48.3% 〔D2〕 | 语音播报是**主输出通道**，文字只是备份（M2 起生效） |
| 手抖、视力下降、听力下降 | 无官方量化数据 `推断` | 点按不要求长按；字号 ≥ 24pt；播报语速可调慢 |
| 可能讲方言 | 无官方量化数据 `推断` | 识别失败必须有免语音兜底，不许硬猜 |

### 2.2 次链路用户（P1 · M2 验收通过后才做）

**定义：25–55 岁、与老人或儿童同住的家庭成员。**

- 数据：手机网民 11.05 亿，占网民 99.7% 〔D7〕—— 这批人不存在可达性问题，问题只在产品是否值得他们用。
- 定位：**辅助启动者**。他们可能在老人身边代为打开、代为提问，然后让老人听答案。
- 结论：不做专属交互，但**不得阻挡他们使用**。青年专属界面见 §7 延后项。

### 2.3 明确的非目标用户

- 专业消防救援人员（他们需要的是装备与战术，不是问答）
- 企业安全生产管理人员（法规合规场景，需求完全不同）
- 儿童独立使用（无监护场景下给出指令存在风险，不做定向优化）

### 2.4 关键判断：为什么终态主链路不能以「青年」为默认

家庭火灾亡人的主体是老人（48.3%），而老人的互联网普及率仅约 52.5%〔D5〕`推断`。若以青年交互习惯为默认（打字、滑动、多轮追问），交付物对**伤亡贡献最大的群体**直接失效。这不是体验差异，是覆盖面缺失。

**但接受一个工程现实**：语音链路（ASR/TTS 选型、噪声、方言）风险最高，先做文字问答可最快验证「知识库 + 拒答 + 分诊」这三个真正决定安全性的环节。因此 M1 做文字、M2 补语音，是**风险排序**，不是降低目标。

## 3. 链路定义

### 3.0 模式判定规则（已定方向，实现方案待确认）

**策略 C：默认进入日常模式；命中危险信号则强制切紧急模式，且用户不可手动关回日常。**

| 项 | 规则 |
|---|---|
| 默认态 | 日常模式 |
| 切换条件 | 输入命中**危险信号**（见下）即切紧急，同一次会话内不回落 |
| 用户可否关闭 | **不可**。只能退出重开进入日常 |
| 切换反馈 | 顶部出现明显色带 + 一行大字「已切到紧急指引」+（M2 起）语音提示 |
| 反向规则 | 紧急模式中不做「看起来没事」的自动降级——宁可多给步骤，不可少给 |

**危险信号的三类来源**（判定技术方案未定，见 §9 D2）：
1. **场景词**：燃气、煤气味、着火、冒烟、触电、溺水、地震、电梯困住……
2. **危重词**：昏迷、没呼吸、大出血、抽搐、叫不醒……
3. **语气信号**：短句、重复、感叹、带「快」「救命」等（`推断`，实现难度高，M2 后评估）

**为什么不用 A（用户自己选）**：老人不会主动判断该走哪条通道，选错代价不对称——误选日常会得到不痛不痒的解释。
**为什么不用 B（纯自动判定）**：漏判时用户没有补救手段。C 保留 A 的兜底（图标按钮永远可点），同时在漏判时不做任何降级。

### 3.1 紧急链路（M2 验收对象）

**一条路径，六步，全程不出现键盘。**

| 步 | 用户动作 | 系统响应 | 硬约束 |
|---|---|---|---|
| 1 | 打开链接 / 切到紧急 | 全屏单按钮「按住说话」，下方图标区（来自 slots 注册表） | 打开到可说话 **≤ 2 次点击**，启动动画 ≤ 1 秒 |
| 2 | 按住说一句话（如「煤气漏了怎么办」） | 显示「在听」＋实时音量反馈 | 松手即发，无需点「发送」 |
| 3 | 松手 | 1 秒内出现「听懂了：燃气泄漏」确认条 | 识别置信度低 → 不猜，转 §3.3 兜底 |
| 4 | 听播报 | TTS 播报 + 同步大字幕，三段：立刻做 / 接着做 / 绝对不要做 | 首句播报 **≤ 3 秒**（自松手计时） |
| 5 | 逐条打勾 | 每条前有大复选框，点一下变「已完成」 | 复选框点击区 ≥ 48×48 px |
| 6 | 需要时拨号 | 「拨打 119」大按钮，点击唤起拨号盘并预填，**由用户自行按下拨出** | 不得尝试自动拨号（H5 平台不允许，见 §6） |

**M1 的临时形态**：第 1 步的「按住说话」换成文字输入框，第 3 步的识别换成关键词匹配，第 4 步只有文字无播报。**其余约束（分段、打勾、拨号、拒答）在 M1 就必须满足**——它们是安全规则，不是语音功能。

### 3.2 日常链路（M1 验收对象）

**目标：跑通最简单的问答系统。**

| 步 | 用户动作 | 系统响应 |
|---|---|---|
| 1 | 打开链接 | 输入框 + 场景入口（来自 slots 注册表）+ 常驻免责 |
| 2 | 输入问题 | 检索知识库，命中则进第 3 步；未命中进 §3.3 |
| 3 | 读回答 | 解释性文字（允许 LLM 组织语言）+ 可选「查看操作步骤」按钮 |
| 4 | 点「查看操作步骤」 | 进入与紧急模式**完全相同**的三段式步骤卡 |

**日常模式的两条边界**：
- 只答应急知识、安全常识、器材使用、预防措施。**超出范围一律拒答并说明擅长范围**，不做开放闲聊。
- 日常模式里若识别出危险信号，**强制切紧急**（§3.0），不能停在一个「温和的解释」上。

### 3.3 兜底路径（与主链路同等优先级）

任何一步失败（识别失败、未命中、网络异常），回到图标区（来自 slots 注册表），点一下直接出对应场景的步骤卡。图标必须带文字标签 + 图形，不依赖识字也能靠位置记忆。

**离线态兜底**：断网时页面若已被缓存，只展示 `offline: true` 的条目，顶部常驻「当前离线，内容为预存版本」；语音功能不可用（见 §6.1）。

## 4. 功能范围（按里程碑切分）

### 4.0 里程碑定义（v1.1 修订，2026-11-19 改为累积式）

> **累积式原则（v1.1 定死）**：每个里程碑 = **继承前版全部能力 + 新增一批能力**。**任何里程碑都不得削减已交付的功能。** 下一节的「必做」只列**新增项**，不重复前版内容。

| 版本 | 继承 | **新增** | 验收对象 | 是否算「主链路跑通」 |
|---|---|---|---|---|
| **M1** | — | 文字问答 + 结构化知识库 + 拒答 + 三段式步骤卡 + 拨号按钮 | 团队自测 | **不算** |
| **M2** | M1 全部 | 语音输入（云 ASR）+ TTS 朗读 + 模式自动判定；**单次判定，不含 ReAct、不含手写引导** | 团队自测 + 界面验收（U1–U8）；**老人实测（V3/V5）延后至 M2.5** | **待验证**（V3/V5 完成后才是；此前对老人可用性无证据） |
| **M2.5** | M2 全部 | 手写输入引导 + ReAct 判定循环（仅日常模式）；验收环境 = 桌面浏览器 | 老人实测（V3/V5） | 是（增强） |
| **M3** | **M2.5 全部** | **Tauri 打包（Windows exe + Android APK）+ 内置全量知识库 + 离线 TTS + 云端中继（D-7）+ 离线语音输入（讯飞 AIKit，v1.5 新增）**；联网时智能能力**不得低于 M2.5** | 断网环境 + 联网环境 | 是（形态升级） |
| **M4** | **M3 全部** | **待定 —— 用户未指定内容，本表不占位猜测。填写前不得动工**（见 `§9 V15`） | 待定 | 待定 |

**M1 的定位是「技术验证」，不是「产品交付」。** 任何对外演示若跳过 M2，必须声明「此版本对老年人不可用」。

**为什么 M2 单独成一个版本、M2.5 另立（2026-11-19 用户裁决）**：M2 要能作为独立可演示的完整版本收口（语音进、语音出、单次判定），M2.5 只在其上叠加交互升级。两者不能混作一个里程碑，否则「语音链路是否打通」与「ReAct 是否有效」两个风险会搅在一起，出问题时分不清是哪一边。

**M2.5 的验收环境是桌面浏览器**（用户裁决 A）。理由：`§9 V8` 实测 Android 手机浏览器**不存在 `speechSynthesis`**，朗读路径在该环境整体缺失；而 `V9` 的 `tauri-plugin-tts` 至今未验证。先用桌面把「语音进出 + ReAct」这个交互证明成立，设备问题留给 M3 打包一次解决。

**M3 的联网 / 断网是两种状态，不是两种产品（v1.1 修正）**：

| 状态 | 智能能力 | 说明 |
|---|---|---|
| **联网** | **必须保持 LLM 判定 + ReAct**，综合准确率不得低于 M2.5 的实测值 | 由云端中继（D-7）承载，不依赖本地 Node 进程 |
| **断网** | 退 L3 字符检索（prevention 3/30、off_scope 18/30、emergency 40/40） | **这是平台物理约束，不是功能削减**。兜底设计（`03` §5）本就是为这种情况存在的 |

> **v1.1 更正**：v1.0 此处曾写「M3 不承诺智能能力」，那是把「断网时的物理退化」误写成了「产品定位的主动削减」，已删除。断网退化属兜底设计的正常生效，联网不得退化。

### 4.1 M1 必做（缺一项连技术验证都不成立）

1. **文字问答输入**（中间态，M2 后降级为次要入口）
2. **快捷图标（注册表驱动，v0.3 改）**：图标不写死在代码里，由 `knowledge/index.json` 的 `slots` 渲染。
   - 当前预置 **10 个槽位**，其中 **9 个已发布（`state: ready`）**：燃气泄漏、老人跌倒、电梯困人、家庭火灾、一氧化碳中毒、烧烫伤、触电、气道梗阻、地震；`drowning` 因 V12 阻塞保持 slot（见 §9 V11/V12）
   - 加场景 = 加一行 slot + 新建 `<id>.json`，**不改前端代码**
   - 无内容的槽位默认隐藏（`show_when_empty: false`），避免用户点开是空的
   - 构建立场：`tools/build_knowledge_js.py` 只把 `ready` 且有 `published` 条目的槽位写进产物，**未发布条目物理上不会进前端**
3. **自建结构化知识库**（JSON，字段见 `docs/02-数据契约.md`）
4. **三段式输出**：立刻做（前 30 秒）/ 接着做 / 绝对不要做
5. **步骤打勾**：防慌乱重复操作
6. **一键拨号**：`tel:` 唤起系统拨号盘，号码已带好，**由用户按下拨出**（不自动拨号，见 §6 段末）
7. **常驻免责**：首屏固定一行，不弹窗、不遮挡按钮
8. **拒答兜底**：知识库外一律不生成步骤，给固定话术 + 拨号按钮
9. **双模式骨架**：日常 / 紧急两条通道 + 危险信号强制切换（M1 用关键词表实现，见 `03` §5；M2 升级为 LLM 语义判定，见 `03` §2）

> **M1 的场景数量不设下限。** 验收看的是「机制正确」而非「场景够多」：只要有 1 个已发布场景能跑通全链路 + 库外拒答 20/20，M1 机制即成立。场景数量属内容进度，不属 M1 验收项。

### 4.2 M2 必做（独立版本：语音进出 + 单次判定）

1. **语音输入**：按住说话 → 云 ASR（`POST /v1/tools/asr`）→ 场景归一
   - 实测依据（2026-11-19）：1.6 秒中文语音，墙钟 891 / 936 / 992 / 1328 ms 多次，识别「煤气漏了怎么办？」完全正确；闭环验证 3/3 全对（`tools/e2e_asr.mjs`）
   - **前提**：页面必须处于安全上下文（`https` 或 `localhost`），`file://` 双击打开拿不到麦克风权限
   - **实现状态（2026-11-19）**：`app/asr.js` 已落地——录音 → 重采样 16k → WAV 编码 → 代理转发；错误分 8 类；两个模式各有入口
2. **TTS 朗读**：可重播、可打断、语速可调慢
3. **识别失败兜底**：置信度低于阈值不猜，回图标
4. **模式判定升级**：关键词表 → 加语义判断
5. **明确的非目标**：**不做 ReAct 循环、不做手写引导**，二者属 §4.25

> **M2 的验收环境限定为桌面浏览器（Windows）。** Android 手机浏览器无 `speechSynthesis`（§9 V8 实测），朗读路径在该环境不存在——这条不是实现缺陷，是平台事实。

### 4.25 M2.5 必做（智能交互升级，叠加在 M2 之上）

1. **手写输入引导**：复用**系统输入法**的手写区，不自建手写板、不接第三方 HWR、不加任何依赖。产出仍是文字，判定链路一行不改
   - **已知风险（必须在老人实测中观察，不许默认成立）**：点输入框默认弹出的是拼音键盘，**不是手写区**。用户须自行切到手写模式。若实测中老人切不过去，则「手写输入」等于不存在——此时需另做引导层（属界面改动，不改本契约）
   - 这条风险登记为 `§9 V14`
2. **工具注册表 + 模型自主调用**（M2.5 的判定形态，2026-11-19 用户定）：各功能模块封装为工具，由模型自主选择调用。**仅限日常模式**（`03` §3.7 已定紧急模式走关键词先判，实测 emergency 40/40）
   - 步数由**模型自主 `finish`** 决定；硬上限只作失控保险丝，**不作为决策依据**，具体数值须实测 P95 后定
   - 每一步必须有**可见进展反馈**（对应 §8 红线 1），不得出现无反馈的纯等待
   - **拨号工具只生成按钮，永不代为拨出**（§6 段末 + §4.6）
   - 出内容的工具必须有查库前置条件；`dial` / `refuse` 作为安全出口不加门槛
   - 工具清单、前置条件门、判据见 `03` §2.5
3. **输入区常驻**（用户 2026-11-19 定）：结果出现后输入区不消失，结果以追加流呈现而非覆盖
   - 三项结构性代价与四个待确认项见 `03` §2.5.8 / §2.5.12（D-10、D-11 **未裁决前不动代码**）
4. **会话记忆**（用户 2026-11-19 裁决 A/A/B/A）：**仅会话内、仅内存，刷新即清**
   - **只存用户原话，不存模型结论**（结论会累积错误且无法察觉）
   - 注入走代理 `context` 字段，**不许前端拼接**（拼接会让上文场景词污染当前句）
   - `scene_locked` 记忆不得改写（S8）；用户说「不是这个」即清空
   - **不做跨会话持久化**，与 §4.6「不做账号体系」一致
   - 设计见 `03` §2.6，判据 M1–M6；风险登记 `§9 V18`
5. **兜底沿用 M2，不新增降级层**：所有失败点落 `03` §5 的三层兜底（L1/L2/L3）+ §3.3 图标区
6. **可缺席要求（硬约束）**：工具调用、记忆、语音在断网时必须能被完整绕过，链路仍成立。**不许出现「没有工具调用就不能用」**

### 4.3 M3 新增必做（软件打包 + 离线 + 云端中继；M3 = M2.5 全部 + 以下）

> 下表**只列新增项**。M2.5 已有的语音输入、TTS、ReAct、手写、拒答、拨号、步骤卡**全部继续有效**，不在 M3 重做，也不许在 M3 被关掉。

1. **Tauri 2 打包**：Windows exe（主）+ Android APK（辅）
2. **内置全量知识库**：注册表内所有已发布条目全部打进安装包（约 20–30KB），不做「只内置一部分」
3. **离线 TTS 朗读**（关键）：
   - Windows：系统 SAPI 语音（Kangkang / Huihui / Yaoyao），默认选女声 Huihui
   - Android：原生 `TextToSpeech`，启动时用 `isLanguageAvailable("zh-CN")` 检查；不可用则给明确提示 + 引导安装语音包
4. **云端中继（D-7，v1.1 新增，M3 硬前置）**：把 M2.5 的本地代理（`03` D-5）改为部署在服务器上的中继服务，承载 LLM 判定 / ReAct / 云 ASR 三类请求
   - **这是 M3 保住联网智能的唯一方式**：打包后没有 Node 进程，原 `127.0.0.1:8787` 必然失效
   - 中继不可达时行为必须与「断网」一致：退 L3，且按 `03` §5.4 顶部提示，**不许静默**
5. **离线输入 = 图标区 + 手写 + 离线语音**（手写走系统输入法，离线可用，见 §4.25 第 1 条；离线语音见 §4.5）
   - **离线语音的前置条件（三条，缺一即回退）**：
     ① **讯飞离线授权已采购到位**（Windows 版**只支持设备授权**，按设备数 + 有效期，需商务流程）
     ② 音频编码链路打通（该 SDK **不支持 PCM/WAV**，只吃 lame / speex / opus / speex-wb）
     ③ Tauri 侧 Rust FFI 绑定可用（SDK 是 **C++ 接口**，不能从 JS 直接调）
   - **回退行为**：任一条件未满足时，离线输入退回「图标区 + 手写」，**不得因此阻塞 M3 交付**
6. **数据版本显性化**：界面固定显示「数据版本：YYYY-MM-DD」，旧数据也要显示
7. **更新机制**：`manifest.json`（版本号 + 校验和）→ 版本不同整包替换 → 校验失败回滚内置版
8. **离线标识**：顶部常驻「当前离线，内容为预存版本」

### 4.5 离线 ASR：M3 做，走讯飞 AIKit 离线 SDK（一档决定，v1.5 改）

> **v1.5 变更（2026-11-19，用户裁决「纳入 M3」）**：本节原为「明确不做」，理由是「无可行方案」。
> 用户提供讯飞 AIKit 离线听写 SDK 后，该理由不再成立，故整节重写。
> **结论从「不做」改为「做」，但增加了三条前置条件与一条回退路径。**

**离线时「必须能听」是硬要求；「能说」（离线 ASR）原为增强项，v1.5 起纳入 M3。**

| 方案 | 判定 | 理由 |
|---|---|---|
| 云端 ASR | 离线失效 | 既成事实 |
| Android 系统 `SpeechRecognizer` 离线模式 | **不可依赖** | 需设备离线语言包，国行机型通常没有（`推断`，V8 待测） |
| whisper.cpp / Vosk 本地模型 | **仍不做** | 体积 40–75MB，需 NDK 编译，100 小时内风险过高 |
| **讯飞 AIKit 离线语音听写** | **采纳（M3）** | 引擎已打包成库，不需自己塞模型；Windows 与 Android 都有官方 SDK |

#### 4.5.1 查证事实（2026-11-19，官方文档）

| 项 | Windows SDK | Android SDK |
|---|---|---|
| 能力 id | `e0e26945b` | `ee62fa27c` |
| 平台 | x64/x86_Windows（同包还含安卓32/64、x86_linux、arm、arm64） | Android 5.0–13（鸿蒙未验证） |
| 语种 | 中英日韩俄法德西泰维阿拉伯 | **仅中英** |
| 授权 | **只支持设备授权** | 设备授权 / 应用授权 |

| 激活 | **首次必须联网**，之后断网可用 | 同左 |
| **音频编码** | **lame / speex / opus / speex-wb（无 PCM/WAV）** | 同左 |

| 帧大小 | ≤ 1024 | — |
| 价格 | **商务定制，无公开报价** | 同左 |

**三条对实现影响最大的事实**：

| # | 事实 | 后果 |
|---|---|---|
| 1 | **Windows 版只支持设备授权** | 按设备数 + 有效期计费，**必须走商务采购**。这是 100 小时内最可能卡住的一环 |
| 2 | **不接受 PCM/WAV** | 现在前端产出的 WAV 不能直喂。要么引入 lame/opus 编码（多一个依赖 + 体积），要么在 Rust 侧转码 |
| 3 | **C++ 接口** | Tauri 需要 Rust FFI 绑定（`bindgen` 或手写 `extern "C"`），**不能用 JS 调用** |

#### 4.5.2 前置条件与回退（缺一即回退，不许阻塞 M3）

| # | 条件 | 未满足时 |
|---|---|---|
| 1 | 离线授权已采购到位 | 回退「图标区 + 手写」 |
| 2 | 音频编码链路打通（lame/opus） | 同上 |
| 3 | Rust FFI 绑定可用 | 同上 |

**回退不是失败**：`§4.3` 第 5 条已写明回退行为，M3 的验收项「断网可用」**不依赖**离线 ASR——
图标区 + TTS 已满足「必须能听」。离线 ASR 属**增强**，做成是加分，做不成不影响 M3 验收。

#### 4.5.3 为什么不改变「必须能听」的优先级

离线 ASR 是「能说」，TTS 是「能听」。若两者抢时间，**先保 TTS**——
`03` D-6 的断网态验收只看「能不能听」，不看「能不能说」。

### 4.6 不做（写进基线以防范围蔓延）

账号体系 / 云同步 / 多语言 / 图像识别 / 开放闲聊 / 位置上报 / 语音唤醒词（"小X小X"）/ 自动拨号 / 离线 ASR

> 语音唤醒词被排除的理由：常听误触发在应急场景会造成误播报，且后台无法持续监听。
> 自动拨号被排除的理由：所有形态（含 Tauri）都不应替用户发起通话，且网页版平台不提供该能力（见 §6）。
> 离线 ASR 被排除的理由见 §4.5。

## 5. 安全规则

**本产品是安全产品，不是问答产品。以下规则优先于任何体验优化。**

| 编号 | 规则 | 可失败的判据 |
|---|---|---|
| S1 | 模型**不得生成**知识库之外的步骤 | 取 20 个库外问题提问，输出步骤数须为 0，且 20/20 命中拒答话术 |
| S2 | 库内答案的每一条步骤必须可回溯到条目 ID | 抽 20 条回答，逐条比对，可回溯率须 100% |
| S3 | **绝对不要做** 段落不得为空 | 遍历全部条目，禁忌项为空的数量须为 0 |
| S4 | 拒答话术固定，不含任何操作步骤 | 库外问题输出中不得出现动词开头的指令句 |
| S5 | 生命危险场景：给关键步骤 + 播报含「同时拨打 120」+ 显式拨号按钮 | 命中 `life_threatening: true` 的条目，播报文本须含该句，缺一即失败 |
| S6 | 免责声明常驻首屏 | 任意路径进入首屏，免责文案可见且不被遮挡 |
| S7 | 日常模式允许 LLM 解释，但**回答里出现的操作动作必须全部来自 `steps`/`never` 字段** | 抽 20 条日常回答，逐句标注操作动作来源，库外动作数须为 0 |
| S8 | 危险信号命中后不可回落日常 | 命中后同一会话内再次输入无害问题，仍处于紧急模式 |
| **S10** | **来源必须机器逐字比对，通过才可发布**（v0.5 新增） | 跑 `tools/check_source_quote.py`：`pass` 才允许 `published`；`fail` 与 `unverified` 一律拒绝发布 |
| **S11** | **机器比对只判"字面一致"，不判专业正确** | `agent_check` 记录中不得出现"顺序正确""医学合理"等专业结论；专业结论只能来自人 |

> **S9 已删除（v0.6）**
> 原条文：「拨号按钮：按场景主推 1 个 + 常驻一行『紧急情况请直接拨 120』」，判据「屏幕上拨号入口数 ≥ 2，主推号码与场景匹配」。
> **删除理由（用户裁决）**：遇到问题直接拿手机拨号，比打开应用、点进场景、再点按钮更符合常识。常驻那一行小字的存在前提是「用户会在应用里找号码」，这个前提不成立。
> **保留的部分**：场景卡内的拨号按钮**不删**，但其依据从 S9 移到 **S5**（生命危险场景须有显式拨号按钮）。两者区别是：按钮作为**步骤卡的一部分**（此刻手里就拿着手机、上下文明确、号码已判定）有价值；**常驻页脚提示**没有。
> **连带影响**：`emergency_number` 字段仍保留（消费者：场景卡按钮 + M2 语音播报），数据契约 §4.2 中「前端另有常驻小字」一句同步删除。

**S5 裁决结果（已定，v0.2）**：保留口头提示「同时拨打 120」。不自动拨号，只播报 + 显示。理由：等待救护车期间若不给任何动作，产品价值归零；提示是把判断权交回用户，不构成误拨风险。

**S9 裁决结果（v0.2 定，v0.6 删除）**：~~按场景主推一个号码 + 常驻一行小字「紧急情况请直接拨 120」。~~
**v0.6 用户裁决：整条删除。** 理由见上表下方说明——真实险情下用户直接拨号，不会打开应用找按钮。**常驻页脚行已从界面移除**；场景卡内的拨号按钮按 S5 保留。

**S10/S11 裁决结果（已定，v0.5）**：审核人数由 2 减为 1（省交叉等待），但 `source_quote_verbatim` 这一项**改由机器判**，人不得手填。

| 检查项 | 谁判 | 理由 |
|---|---|---|
| 步骤顺序对不对 | **人** | 无法机械判定，机器判会产生新幻觉 |
| 禁忌项是否抓准关键风险 | **人** | 需要专业判断 |
| `quote` 是否逐字存在于原文 | **机器** | 人肉眼比对上百字必漏，机器不会 |

**核心原则**：`unverified`（抓不到原文）**不等于** `pass`。抓不到就如实标 `unverified` 转人工——**把"没查出问题"当成"没问题"是本项目最危险的错误。**

**S1/S2/S7 的关系**：S1 管「紧急模式不许生成」，S7 管「日常模式不许生成动作」。两条加起来才是完整约束——**允许解释，不允许发明动作**。

| 单条步骤字数 | ≤ 20 字 | M1 | 脚本遍历知识库全部步骤 |
| 步骤条数 | 每段 3–7 条 | M1 | 同上 |
| 最小字号 | ≥ 24pt | M1 | 浏览器计算样式读取 |
| 复选框点击区 | ≥ 48×48 px | M1 | 同上 |

| 方言识别 | 不使用方言，但**识别失败必须兜底** | M2 | 普通话不清朗读 10 次，失败时须进入图标兜底且**不得输出错场景步骤**（错场景次数须为 0） |

> **无法自动拨号（平台限制 + 设计选择）**：网页形态下只能通过 `tel:` 唤起系统拨号盘，最后一步必须由用户点按确认。软件形态技术上可以发起通话，但**仍不自动拨号**——无法判断用户是否处于真实险情，代为拨号可能占用急救线路。两种形态统一为「界面跳转 + 预填号码 + 用户自行拨通」。

### 6.2 离线语音的平台事实（v0.3 新增，决定 M3 可行性）

| 平台 | 离线中文 TTS | 依据 | 结论 |
|---|---|---|---|
| **Windows 10/11** | ✅ 有 | Microsoft 官方支持表：Chinese (Simplified) → 男 Kangkang / 女 Huihui、Yaoyao 〔D10〕 | **可确定**，无需额外部署 |
| **Android** | ⚠️ 取决于设备 | 未见官方统一说明 | **风险项**，必须在目标机型实测（V8） |
| **iOS** | — | 需签名证书 + Mac，100h 内不做 | 排除 |

**Android 的两条规避原则（M3 实施时执行）**：
1. 不依赖 WebView 的 `speechSynthesis`，改调 **Android 原生 `TextToSpeech`**。
2. 启动即检查 `isLanguageAvailable("zh-CN")`；不可用时**明确告知**并引导安装语音包，**不允许静默失败**（静默失败 = 用户以为没声音 = 等于没有产品）。

**断网时的能力矩阵**：

| 能力 | 联网 | 断网 |
|---|---|---|
| 图标 → 步骤卡 | ✓ | ✓ |
| 朗读步骤 | ✓ | ✓（系统 TTS） |
| 语音提问 | ✓ | **✓ 条件性**（讯飞 AIKit 离线 SDK，§4.5）；**前置不满足则退化为 ✗**，走图标区+手写 |
| 日常问答的解释文字 | ✓（LLM） | ✗（仅内置的 `daily` 文案） |
| 内容更新 | ✓ | ✗（用内置旧版本，界面显示版本日期） |

> **「条件性 ✓」的含义（v1.5 新增）**：离线语音提问依赖三条前置（授权、音频编码、Rust FFI），
> 任一不满足即回退为 ✗。**M3 的验收项是「断网可用」，由图标区 + TTS 满足，不依赖离线语音**。
>
> 离线数据的「空窗期」：用户装完不联网，内置数据会一直是旧版本。**事故时旧数据好过没数据**，但界面必须显示数据版本日期（§4.3 第 5 条），不许隐藏。

## 8. 违反基线的红线

出现以下任一情况，视为偏离需求，须停机讨论：

1. 出现「请稍等，正在思考」之类的等待文案而没有即时反馈
2. **M2 之后**紧急模式任一环节必需键盘（M1 期间键盘是已知临时状态，见 §4.0）
3. 模型在库外问题中输出了任何一句操作指令（S1）
4. 模型在日常回答中发明了知识库里没有的动作（S7）
5. 为通用性而增加开放闲聊能力
6. 危险信号命中后允许用户手动切回日常模式（S8）
7. 把 M1 交付物对外称为「主链路跑通」

**删除 S9 的理由**：真实险情下用户直接拿手机拨号，不会先打开应用、点进场景、再点按钮。「入口数 ≥ 2」这条判据在追一个不存在的行为。

**不删的东西**：场景卡内的拨号按钮。它和页脚常驻行的区别是——用户此刻手里正拿着手机、看的正是这张卡、号码已由场景判定好；此时点一下是有用的。依据从 S9 移到 S5（生命危险场景须有显式拨号按钮）。

**为什么确认「字符匹配是过渡态」**：M1 实现中字符匹配暴露两个硬缺陷——① 中文无词边界，「打不着火」被「着火」误命中（已加否定前缀检测临时修掉）；② 「怎么预防燃气泄漏」含「燃气」被强制切紧急，而按 §3.0 策略 C 又不能降级。两个问题都源于「没有语义」。LLM + RAG 是正解，不是优化项。

**未变的结论**：M1/M2/M3 里程碑、Tauri 形态、离线只做 TTS、S1/S7 的「不许发明动作」红线。
