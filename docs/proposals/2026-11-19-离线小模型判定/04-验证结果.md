## 2. 复现（可逐条粘贴执行）

```bash
# 1) 依赖：只装探针目录，不动根 package.json
cd tools/probe/intent_probe
npm install @huggingface/transformers@3.7.0 --ignore-scripts --no-audit --no-fund

# 2) 模型：主站不可达，必须走镜像（实测 huggingface.co 12s 超时 / 返回 000）
B=https://hf-mirror.com/Xenova/bge-small-zh-v1.5/resolve/main
mkdir -p models/bge-small-zh-v1.5/onnx
for f in config.json tokenizer.json tokenizer_config.json special_tokens_map.json; do
  curl -sSL -o models/bge-small-zh-v1.5/$f "$B/$f"
done
curl -sSL -o models/bge-small-zh-v1.5/onnx/model_quantized.onnx "$B/onnx/model_quantized.onnx"

# 3) 静态服务（仓库根目录起，端口任意）

# 4) 打开最终探针页
#    http://127.0.0.1:8911/tools/probe/intent_probe/probe-page3.html
#    结果渲染在页面；window.__RESULT.rows 含逐条分数（本目录 data/逐条结果.tsv 即由此导出）
```

**校验模型下载完整**：`stat -c%s models/bge-small-zh-v1.5/onnx/model_quantized.onnx` 应为 `24010842`。

## 3.1 ⚠️ 口径标注（2026-11-19 由核对者补，不改任何数字）

上面「规则闸 detectDanger 实测」那三行是 **`detectDanger` 的命中条数**，**不是 action 准确率**。两者差得很远，混引会得出相反结论：

| 口径 | emergency | prevention | off_scope |
|---|---|---|---|
| `detectDanger` **命中**（上方原始输出） | 40/40 | **20/30** | 11/30 |
| `run_eval.mjs --engine=l3` 的 **action 准确率** | 40/40 | **3/30** | **18/30** |

**prevention 命中 20 条、最终却只对 3 条**，原因：这 20 条含场景词（「怎么预防**煤气**泄漏」），闸门放行后仍会被字符检索命中场景并出急救步骤卡 → 只有 3 条侥幸判成 daily。

**这恰好说明字符匹配的失效点不在「闸门」而在「命中后无法区分意图」** —— 也正是本提案要解决的核心，不是对提案的反驳。

核对者复现（2026-11-19，`run_eval.mjs` 修好加载列表后）：

```
node tools/eval/run_eval.mjs --engine=l3
  emergency 40/40 | prevention 3/30 | off_scope 18/30 | 综合 61.0%
```

复合策略与阈值细扫结果（`类中心 + 规则兜底` 那一栏）由 `data/逐条结果.tsv` 离线复算得到，逐条可核：

## 4. 未验证项（不许当结论用）

| # | 未验证 | 为什么重要 | 怎么补 |
|---|---|---|---|
| **L1** | 阈值 0.045 在**同一批 100 条**上选出 | 存在过拟合，评委可问「你怎么调的阈值」 | 用 `08 P9` 的 20 条独立样本（「有股味道，头有点晕」「我妈倒了，叫不醒」）重标定；**在此之前 85% 不得对外当结论** |
| **L2** | 只在 Chrome + WASM 单线程测 | Tauri 用 WebView2、APK 用 Android WebView，WASM 支持与性能都可能不同 | 打包后在同一页上重跑一次，记录 loadMs 与 p50 |
| **L3** | 内存峰值未测 | 22.9MB 模型 + WASM 运行时，老人机可能吃不消 | DevTools Performance 录制，取 JS heap 与 WASM memory 峰值 |
| **L4** | 长句 / 多轮口语未测 | 评测集平均句长 7.3 字 | 造 20 条 20 字以上的口语长句单测 |
| **L5** | 原型由本人手写、且知道评测集话题 | 原句未复用，但话题覆盖受此影响 | 请第三方（队友）独立写一套原型，看两组数字差值 |
| **L6** | `SCENE_TAU`（场景判定的最低分阈值）未标定 | `02` §4 里留的是占位值 | 实现阶段先跑一次扫描再定值 |
| **L7** | 打包后总体积未实测 | 34.7MiB 是分项相加 | Tauri 出包后 `du` 实测 |

## 5. 过程中踩的坑（写给后来人）

| # | 现象 | 原因 | 处置 |
|---|---|---|---|
| 1 | `npm install @huggingface/transformers` 首次跑 420s 超时 | 新版 4.3.2 依赖 `onnxruntime-node` **原生二进制**，在本机下载极慢 | 降到 **3.7.0** + `--ignore-scripts` 跳过原生二进制，改走 WASM |
| 2 | `npm install` 加了 `--ignore-scripts` 后，`node probe.mjs` 报 onnxruntime 缺二进制 | 同上 | **放弃 Node 版，改跑浏览器版**（更接近真实运行环境，结果反而更有参考价值） |
| 3 | `probe-page2.html` 首次运行报 `Cannot read properties of null (reading 'length')` | `variants` 里的函数签名是 `(v, c)`，但调用处传的是 `(null, {text})` —— 第一个参数恒为 null，进 `cos()` 就崩 | 改成先用 `caseVecs[i]` 一次算好每行结果，`variants` 只按行取，不再传向量 |
| 4 | `probe-page2.html` 场景对照显示「现字符规则 0/70」 | 调错了入口：`rankByRules(entries, text)` 需要 entries 参数，传的是 `(text, null)` | 单独跑一次正确入口，得 **54/70 = 77.1%**，已订正进 `03` §5 |
| 5 | `probe-page2.html` 规则闸显示「全部 0/40」 | 用了 `window.R`，实际导出名是 `window.RETRIEVAL` | 订正后 emergency **40/40**，与文档一致 |
| 6 | huggingface.co 直接超时 | 本机网络不可达主站 | 全部走 `hf-mirror.com`（实测 200 / 0.8s） |

> 第 4、5 条是**探针自己出错**，不是模型结论。订正前后的数字都在过程记录里，没有直接改结果不留痕。

## 8. 一句话总结

**模型在「判对预防类」上有确定收益（3/30 → 25/30），在「判对紧急」上不能替代规则（必须兜底），在「场景定位」上有最大收益（77.1% → 92.9%）。** 三项收益的真实性受 L1（阈值过拟合）约束，需要 20 条独立样本才可定论。
