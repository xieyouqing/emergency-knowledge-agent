## 1. 评测集本身

| 项 | 值 |
|---|---|
| 文件 | `tools/eval/cases.json` |
| 样本数 | 100 |
| 分组 | emergency 40 / prevention 30 / off_scope 30 |
| 总字数 | **733 字** |
| 去重汉字 | 257 个 |
| 平均句长 | **7.3 字** |
| 字段 | `id / text / group / expect_intent / expect_scene / expect_action / expect_action_note` |

**这张表最重要的信息是「733 字」。** 它同时说明两件事：

1. 语料太少，**训练分类器不可行**（无独立测试集，`01` §4 C 条被否决的直接理由）
2. 句长 7.3 字，是中文短句里最难的一档——没有上下文、没有虚词，模型只能靠词义。**本提案的数字是在最不利条件下取得的。**

## 2. 原型设计（这是全部效果差异的来源）

三轮迭代，**决定结果的是原型配比，不是模型**。

### 2.1 失败轮回（保留，避免重踩）

| 轮 | 原型设计 | 总准确 | emergency | prevention | off_scope | 死因 |
|---|---|---|---|---|---|---|
| V1 | 每类 4 条抽象元语句 | 71% | **26/40** | 23/30 | 22/30 | 原型是「我家现在正在发生危险」这类元陈述，与真实口语距离远，三类分数全挤在 0.45–0.60 |
| V2 | 由知识库条目衍生（steps / daily.prevention） | 64% | 34/40 | 30/30 | **0/30** | 原型条数 11 / 11 / **1**，严重失衡 → 只要有领域词就判 prevention |
| **V3** | **三类各 8 条平衡原型** | **82%**（零兜底） | 30/40 | 29/30 | 23/30 | — |

**V2 那轮值得单独记一句**：prevention 到了 30/30 满分，但 off_scope 全灭。总分反而比 V1 低。如果只看单组就宣布成功，会得出完全错误的结论。

### 2.2 最终使用的原型句（全文，共 24 条）

```
ongoing:
  现在已经出事了，需要马上告诉我下一步做什么
  现场正在漏气，味道很浓，还在往外冒
  火已经起来了，烟很大，控制不住
  人已经倒在地上了，喊也不应
  有人受伤了，正在流血，需要立刻处理
  现在正在发生的危险，我只有几十秒时间
  事故刚刚发生，现在还在持续，人还在里面
  眼前这个情况很危险，立刻该怎么办

prevention:
  平时怎么做才能不发生这种事
  日常该注意什么，有哪些隐患要提前排除
  多久检查一次，怎么保养维护
  要不要装一个，装了有没有用
  如何避免以后家里再出这种事
  家里有老人，平时生活上要注意什么
  这样做危不危险，算不算隐患
  怎么提前准备，出事了才不慌

off_scope:
  这笔钱怎么交，一共多少钱
  去哪里办理，需要带什么材料
  怎么投诉，找哪个部门反映
  哪个牌子好，买哪个更划算
  陪我说说话，讲个笑话解解闷
  帮我写一份申请，改一下措辞
  今天天气怎么样，适合出门吗
  这个能不能报销，能赔多少钱
```

**零泄漏声明**：这 24 句全部手写，与 `cases.json` 的 100 条无一句重复。评测集只用于打分，不参与构建任何原型。

### 2.3 上界参考（不可部署）

## 4. 兜底阈值（0.045 的来历）

| 阈值 | 总准确 | emergency | 备注 |
|---|---|---|---|
| 0（不兜底） | 82% | 30/40 | 模型独裁 |
| 0.01 | 86% | 34/40 | |
| 0.02 | 87% | 36/40 | |
| 0.025 | 88% | 37/40 | |
| 0.03 | **89%** | 38/40 | 总分最高点 |
| 0.035 | 88% | 39/40 | |
| 0.04 | 88% | 39/40 | |
| **0.045** | **85%** | **40/40** | ← 采用 |
| 0.05 | 84% | 40/40 | |
| 0.06 | 80% | 40/40 | 开始过度干预 |

**为什么不取 0.03（总分最高）**：0.03 时 emergency 38/40，漏掉 2 条紧急。用 4 个百分点的总分换 2 条紧急召回，方向错了。**0.045 是「紧急召回恰好回到 40/40」的最小阈值**，在此之后总分才随阈值上升而下降。

## 5. 场景定位（这一项的收益比意图更大）

同一批 70 条（`expect_scene` 非空）：

| 方案 | 准确率 | 零命中条数 |
|---|---|---|
| 现字符规则 `RETRIEVAL.rankByRules` | 54/70 = **77.1%** | **14 条返回空** |
| 模型原型方案 | 65/70 = **92.9%** | 0 |

### 5.1 字符规则零命中的 14 条（真实用户会说的话）

```
E003 厨房有股臭鸡蛋味      E011 我妈在卫生间摔了
E014 被困在电梯里了（误判 earthquake）  E022 锅烧起来了
E037 有人落水了            E038 小孩掉水里了
P006 家里地面怎么防滑      P013 家里怎么防火
P014 灭火器怎么选          P015 烟感器有用吗
P023 插座要不要装保护盖    P025 老人吃饭怎么防噎（误判 fall_elderly）
```

**这 14 条直接对应 `08` §5.1 记录的两个硬缺陷**，本提案结构性消除它们，不是打补丁。

### 5.2 模型判错的 5 条

| 样本 | 期望 | 判成 | 说明 |
|---|---|---|---|
| E022 锅烧起来了 | fire_home | scald_burn | 「锅烧起来」语义确实介于两者之间，需人工裁 |
| P006 家里地面怎么防滑 | fall_elderly | earthquake | 明显错误，原型缺「防滑/跌倒预防」表述 |
| P015 烟感器有用吗 | fire_home | co_poisoning | 烟感 vs 一氧化碳报警器，原型区分不足 |
| P018 炭火取暖要注意什么 | co_poisoning | fire_home | 同上 |
| P023 插座要不要装保护盖 | electric_shock | elevator_trapped | 明显错误，原型缺「插座/保护盖」 |

**这 5 条是可改进项，不是模型极限**：P006 与 P023 都是「原型里缺这个说法」，补一句原型就能修。这与 V2 的教训一致——**原型覆盖度是主要变量**。

## 6. 性能

| 指标 | 实测 |
|---|---|
| 模型加载（冷，首次进入页面） | 1377 ms |
| 模型加载（热，二次进入） | 536 ms |
| 单句嵌入 p50 | **21 ms** |
| 单句嵌入 p95 | 35 ms |
| 嵌入维度 | 512 |
| 模型文件 | **24,010,842 B = 22.9 MiB** |

**与 3 秒预算的关系**：单句 21ms 占 0.7%。加载 0.5–1.4s 不能进「首屏 1 秒」预算，所以必须懒加载（`02` §5）。

## 8. 规则闸 `detectDanger` 实测（顺手核对文档里的数）

| 组 | 命中 | 与 `08` 记载 |
|---|---|---|
| emergency 40 | **40/40** | 一致 |
| prevention 30 | 20/30 | 这 20 条是「怎么预防」被切紧急的来源 |
| off_scope 30 | 11/30 | 「煤气费怎么交」这类假命中 |

**40/40 是全项目唯一全对的信号**，这正是它必须保留为兜底、而不能被模型替代的原因。

## 9. 数据可信度自评

| 项 | 评级 | 理由 |
|---|---|---|
| 22.9 MiB 体积 | **高** | 文件 `stat` 实测 |
| 21ms / 35ms 延迟 | **高** | 20 次取 p50/p95，同机同环境 |
| 85% 总准确 | **中** | 阈值在同一批 100 条上选的，存在过拟合风险（见 `04` §4 L1） |
| 92.9% 场景 | **中** | 同一批内评测，无独立测试集 |
| 40/40 紧急召回 | **中高** | 与规则一致性交叉验证，但仍属同一批 |
| 34.7 MiB 总体积 | **中高** | 各项实测，但打包后是否还需额外运行时未验 |
