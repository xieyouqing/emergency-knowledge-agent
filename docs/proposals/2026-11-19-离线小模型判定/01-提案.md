# 01 · 提案：离线判定层引入内置小模型

> 版本 v1.0 ｜ 2026-11-19 ｜ 状态：待裁决（P-1/P-2/P-3）
> 本文只回答：**为什么要改 / 改成什么 / 为什么不选别的**。实施细节在 `02-实现方案.md`。

---

## 1. 问题：断网时判定会静默出错

现有离线判定只有字符匹配（`app/retrieval.js` 的 `detectDanger` + `scoreEntryByRules`）。在 100 条评测集上的实测：

| 分组 | 判定正确 | 说明 |
|---|---|---|
| emergency 40 条 | **40/40** | 危险词表覆盖良好，这是全项目最可靠的一路信号 |
| prevention 30 条 | **3/30** | 「怎么预防燃气泄漏」因含「燃气」被强制切紧急 |
| off_scope 30 条 | **18/30** | 「煤气费怎么交」这类假命中 |

**后果不是「用不了」，是「用错了还不知道」。** 老人断网说「怎么预防煤气中毒」，系统给出「立刻关阀门、开窗」的紧急步骤卡。用户无法察觉这是误判。

`08` §5.1 已记录两个硬缺陷：

| 现象 | 根因 |
|---|---|
| 「汽车打不着火」被判成家庭火灾 | 中文无词边界，`着火` 命中子串 |
| 「怎么预防燃气泄漏」被强制切紧急 | 含「燃气」即命中危险信号，且策略 C 不许降级 |

两者同源：**字符匹配只能判断「出现了什么字」，不能判断「在说什么事」。**

## 2. 约束：产品形态不允许把 LLM 带到离线

| 约束 | 出处 |
|---|---|
| 断网必须可用（TTS 播报 + 图标区 + 语音输入） | 用户 2026-11-19 裁决：离线是兜底保障 |
| 紧急链路首句播报 ≤ 3 秒 | `01` §6 |
| 设备是老人机 / 低配 Windows，不能假设有 GPU | `01` §2.1 |
| 断网时无任何云服务 | `01` §6.2 |

所以离线判定必须满足：**本地、小、快、可解释、不随场景数增长而变复杂。**

## 3. 方案：规则闸 + 小模型原型相似度 + 图标候选

```
输入文本（键盘 / 云 ASR / 离线 ASR）
  │
  ├─ L0 规则闸  detectDanger()                        ← 保留，不删
  │      实测 emergency 40/40。危险信号命中即视为「疑似紧急」，
  │      但不再独裁结果，只作为 L1 的兜底修正项。
  │
  ├─ L1 小模型（bge-small-zh-v1.5 q8，22.9MiB）
  │      意图：ongoing / prevention / off_scope 三类原型 → 类中心余弦
  │      场景：10 个槽位原型 → 取最高分
  │      兜底：规则命中 且 模型非 ongoing 且 margin<0.045 → 强制 ongoing
  │
  ├─ L2 图标候选区
  │      多命中 / 低分时列出候选，不猜。零额外配置，随场景数线性展示
  │
  └─ L3 图标区兜底（现成，不动）
```

### 3.1 四个固定量，与场景数无关

| 固定量 | 数量 | 场景 10→100 时 |
|---|---|---|
| 意图原型组 | 3 组 × 8 条 | 不变 |
| 兜底阈值 | 1 个（margin 0.045） | 不变 |
| 危险词表 | 1 张（现成 `DANGER_RULES`） | 基本不变 |
| 兜底出口 | 1 个（图标区） | 不变 |

**这一条是对「确认条方案」的否决理由**：确认条要为每个场景写一句确认文案，复杂度 O(场景数)；本方案是 O(1)。

### 3.2 为什么「兜底」必须存在

模型单独使用的实测（`03` §2.3）：

| 方案 | 总准确 | emergency |
|---|---|---|
| 模型类中心，零兜底 | 82% | **30/40** |
| 模型类中心 + 规则兜底 | 85% | **40/40** |

模型把 10 条紧急判成了「无关」或「预防」。在应急产品里这是不可接受的退化，**所以 L0 不能删、不能降级为提示**。

兜底规则的具体形式：

```
if (ruleHit(text) && modelPred !== 'ongoing' && margin < 0.045) pred = 'ongoing'
```

- 只在「模型拿不准」（margin 小）时才由规则改写，模型确信时不干预
- 阈值 0.045 的来历见 `03` §2.4：它是「emergency 恰好回到 40/40」的最小值

## 4. 被否决的方案

| 方案 | 否决理由 | 依据 |
|---|---|---|
| **A. 保持字符匹配** | prevention 3/30，离线闭环不成立；两个硬缺陷无法结构性消除 | `03` §2.1 |
| **C. 自训小分类器（字 n-gram + 导出 JSON）** | 现有语料仅 **733 字 / 100 条**。训练集与测试集无法分离，训出来也无法自证 | `03` §6 |
| **D. 在浏览器里跑量化 LLM** | 最小可用中文模型也远超 100MiB，加载与推理都击穿 3 秒 | 未实测，按体积直接排除 |
| **E. 云 ASR + 云端意图分类** | 断网即废，与「离线是兜底」直接冲突 | `01` §6.2 |
| **F. 为每个场景写确认文案** | 复杂度 O(场景数)，随数据增长变复杂 | 用户 2026-11-19 指出 |
| **G. sherpa-onnx 的 WASM 版做判定** | 官方 release 的 11 个 wasm 包全是 TTS 模型，**无 ASR/意图产物**；要自己 emscripten 编译 | 官方 release 资产清单实测 |

> G 只针对「判定」这条用途。**离线 ASR 用 sherpa-onnx 的原生 exe / AAR 仍然可行**，属另一个提案，不冲突。

## 5. 与「离线语音识别」的分工

两者都是 ONNX，模型独立，互不依赖：

| 组件 | 模型 | 体积 | 管什么 | 提案 |
|---|---|---|---|---|
| sherpa-onnx | 中文 ASR 模型（体积待实测） | 15–40MB（推测，未核实） | 声音 → 文字 | 另立 |
| bge-small-zh | 意图/场景 embedding | **22.9MiB（实测）** | 文字 → 意图 + 场景 | **本提案** |

**可以分别落地。** 只做本提案：断网能用键盘/手写输入并判对。只做 sherpa：断网能说话但仍判不准。两个都做才算完整离线闭环。

## 6. 边界：本提案不解决的部分

| # | 不解决 | 现状 |
|---|---|---|
| 1 | 长句、多轮、方言口语 | 100 条平均句长 7.3 字，是这类模型最难的情形；长句未测 |
| 2 | 「多命中」场景的仲裁 | 「厨房有股味道，我妈晕倒了」会走图标候选，不自动选第一个 |
| 3 | 生成能力 | 意图判定只定「走哪条通道」，不生成任何文字；S1/S7 红线不变 |
| 4 | 老人可用性 | 本提案不改变 V3/V5 未实测的事实 |

> **第 2 条顺带修掉一个现有缺陷**：`detectDanger` 现在遇第一个命中就 `return`，多命中被静默丢弃。L2 图标候选要求 `detectDanger` 返回**数组**，这个改动属本提案范围（`02` §2.3）。
