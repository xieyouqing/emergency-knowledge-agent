## 1. 阻断级问题

### A1 · 「场景 +11 条」的基线口径错误，真实收益是 +4 条

**这是本次审核最重要的一条。**

**文档的声称**

| 出处 | 原文 |
|---|---|
| `README` 一页速览 | 「场景定位（70 条）｜ 77.1%（14 条零命中）｜ **92.9%** ｜ **+11 条**」 |
| `03 §5` | 「现字符规则 `RETRIEVAL.rankByRules` ｜ 54/70 = **77.1%** ｜ **14 条返回空**」 |
| `01 §5` 一句话总结 | 「在「场景定位」上有最大收益（77.1% → 92.9%）」 |

**问题：`54/70` 在产品里不是一个存在的基线**

`app/app.js:181-183`：

```js
var targetId = danger ? danger.id : null;
var entry = targetId ? ENTRIES[targetId] : bestMatch(text);
```

→ **危险信号命中时，场景直接取 `danger.id`，根本不走检索。** 本提案也明确保留 L0（`01 §3`、`02 §5`）。所以产品里「无模型」时的场景准确率 = 「危险命中用 danger.id」+「未命中时用检索」，不是「全部用 rankByRules」。

**我实测了这个真实基线**（命令见 §7）：

```
node tools/eval/run_eval.mjs --engine=l3
  ...
  ② 场景准确率      80.0%  (80/100)
  === 场景识别错误（20 条，与 action 对错独立）===
      P006 / P013 / P014 / P015 / P023 / P025 / P026 / P030   ← 带 expect_scene 的错，全为 P 组
      O001–O012（12 条）                                       ← off_scope 被误给场景
```

70 条（`expect_scene` 非空）中错 8 条，全部是 prevention → **规则基线 = 62/70 = 88.6%**，不是 54/70 = 77.1%。40 条 emergency 全部经 `danger.id` 判对。

**把两套方案放到同一口径下重算**

| 口径 | emergency（40） | prevention（30） | 合计 |
|---|---|---|---|
| 产品实际规则基线（L0 覆盖 + 检索） | 40/40 | 22/30 | **62/70 = 88.6%** |
| 模型裸判（无 L0，`03 §5` 的 65/70） | 39/40 | 26/30 | 65/70 = 92.9% |
| **组合方案（L0 保留 + 模型接管无危险信号时的场景）** | **40/40** | **26/30** | **66/70 = 94.3%** |

复算依据（`data/逐条结果.tsv`）：模型场景错的 5 条 = `E022` + `P006/P015/P018/P023`。其中 `E022「锅烧起来了」` 被模型判成 `scald_burn`，但 L0 会强制走 `danger.id = fire_home` → 组合后自动修回。故组合 = 40 + 26 = 66。

**结论：真实收益 = 66/70 − 62/70 = +4 条（+5.7 个点），不是 +11 条（+15.8 个点）。**

**为什么这不推翻提案，但必须改**

- 结论方向不变：模型在 prevention 场景上 22/30 → 26/30 确有收益（+4 条），且这是唯一能覆盖「防滑 / 烟感 / 保护盖」这类表述的路径。
- 但「+11 条」是拿模型跟一个产品里不存在的基线比，**属对外陈述错误**。评委一问「你的基线怎么跑的」就崩。
- 顺带修掉 `03 §5` 与 `run_eval.mjs` 的**双标准问题**：同一份代码，两处报出 77.1% 和 80.0%/88.6%，说明「场景准确率」在项目里没有唯一定义。这属 `CODEBUDDY.md` §6「验收标准不许含糊」。

**建议改法**（改数字，不改结论方向）

```
`03 §5` 换表：
  口径一（纯检索，仅用于对照原型质量）：54/70 —— 注明「产品不走这条路径」
  口径二（产品实际，L0 覆盖 + 检索）：62/70 = 88.6% ← 这才是基线
  本方案（L0 保留 + 模型）：66/70 = 94.3% → 收益 +4 条
`README` 一页速览同步改为「+4 条」，并加脚注说明 40 条 emergency 场景不经检索。
`01 §5` 一句话总结同步。
```

**需要你裁一件事**：`03 §5` 的 54/70 当初是怎么跑出来的，现已无法复现（当前代码给 62/70）。这两个数差 8 条，**我倾向于以 `run_eval.mjs` 的 62/70 为准**（它与产品共用路由，`run_eval.mjs:172-186` 注释明写了「测的与用的必须是同一个东西」这条教训），置信度 8 成。但这是**改既有文档的数字**，属一档，等你定。
