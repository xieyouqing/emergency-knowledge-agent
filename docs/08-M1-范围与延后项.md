## 3. 本轮技术形态（M1 阶段临时决定）

**零依赖静态单页：`index.html` + `app.js` + `style.css`，双击即开，无需 `npm install`、无需构建。**

理由：
1. M1 只做文字问答，不需要框架的响应式与路由能力，用 `DOM` 直接渲染 3 个场景足够；
2. 100 小时工期下，少一层工具链就少一类故障（node 版本、依赖下载失败、构建产物路径）；
3. **与 M3 的 Tauri 不冲突**——Tauri 前端就是静态资源，`index.html` 可直接作为 `frontendDist`。

> 若后续要加语音与动画，再评估是否引入框架。规则是：**引入依赖必须换来一项当前无法实现的能力**，不能只为写起来舒服。

## 5. 检索与判定的演进路线（字符匹配 → LLM + RAG）

> **用户裁决（2026-11-18）**：「后面引入大语言模型就可以解决，后面 RAG 也要，不要用字符匹配很不灵活。」
> 结论：**M1 的字符匹配是过渡态，不为它打补丁。** 本节记录为什么、以及换过去时要防住什么。

### 5.1 字符匹配在 M1 暴露的两个硬缺陷

| # | 现象 | 根因 | M1 的处理 |
|---|---|---|---|
| 1 | 「汽车打不着火」被判为家庭火灾 | 中文无词边界，`着火` 命中 `打不着火` 子串 | 加否定前缀检测（`不/没/别/未`、`打不`）临时修掉。**这是补丁，不是解法** |
| 2 | 「怎么预防燃气泄漏」被强制切紧急模式 | 含「燃气」即命中危险信号；按 `01` §3.0 策略 C 又不许降级 | **不处理，保持契约行为**。等 LLM 语义判定 |

**两个缺陷同源**：字符匹配只能判断「出现了什么字」，不能判断「在说什么事」。「打不着火」和「着火了」共享两个字符但语义相反；「预防泄漏」和「正在泄漏」共享同一个词但意图相反。**这正是用户判断的依据。**

### 5.2 目标架构（M2 实施）

**完整方案见 `docs/03-技术方案.md` §1–§6**（意图二维判定、父子文档、阈值硬筛、生成权限矩阵、降级路径、评测对照）。此处只保留结论性摘要。

```
用户输入
   │
   ├─→ [L1 判定层] LLM 输出标签 {scene, intent, confidence}，不生成内容
   │       └─ 三维取值：ongoing / prevention / off_scope   ← 替换 DANGER_RULES 字符表
   │
   ├─→ [L2 检索层] 父子文档：L2 子块向量召回 top-3 → 阈值硬筛（不够一条不进）
   │                → 按 parent_id 聚合 → L1 父文档整条注入
   │
   ├─→ [L3 生成层] 紧急：只许选/排序/精简；日常：可基于 daily 扩写
   │
   └─→ 断网时回退到 M1 字符匹配 + 关键词判定（降级，不是替换）
```

**三条不可让步的约束**（详见 `03` §1）：判定层只出标签不出文字 / 命中后注入父文档整条 / 阈值不够一条都不进。

**关键设计约束（推断，需实测验证）**：断网时不能没有兜底。所以 `DANGER_RULES` 和 `scoreEntry()` **不删，退为离线降级路径**。这与 `01` §6.2「离线只做 TTS 不做 ASR」一致——离线时用户点图标，不进检索。

### 5.3 RAG 引入后必须守住的红线（这是最大的风险点）

> **父子文档方案的完整定义见 `03-技术方案.md` §3。** 下面是最初识别的风险，`03` 已给出结构性解法（子块切分点在字段边界、`steps` 三段必须同块、注入永远整条）。

**风险（置信度 8 成）**：RAG 的常规做法是「文本分块 → 检索 top-k 块 → 拼进 prompt」。如果**把步骤也分块**，就会出现这种事故：

```
检索命中：next 段的一条「情况严重就在室外打 119」
但没命中：never 段的「不要开灯或关灯」「不要用明火试漏」
→ LLM 拿到半截知识，可能编造出「先开灯看看哪里漏」这种致命步骤
```

**硬规则（建议写进 `02-数据契约` §4.4 的补充条款）**：

| # | 规则 | 为什么 |
|---|---|---|
| R1 | **分块只用于「定位是哪个场景」，不用于「回答哪些内容」** | 命中场景后，整条 entry 注入，`steps`/`never`/`source` 一个字段不少 |
| R2 | **紧急模式下 LLM 无生成权**，只做「从给定 steps 里选、排序、精简原文」 | `01` §1.1 已有此规定，RAG 不得作为放宽理由 |
| R3 | **检索结果必须带 `id` 与 `source.quote`**，可回溯到条目 | S2 要求可回溯率 100% |
| R4 | **检索不到 → 拒答**，不许让 LLM「根据常识补充」 | S1 红线 |

**R2 的可验证判据**：抽 20 条紧急回答，逐句在对应条目的 `steps`/`never` 里找原文，找不到的句子数须为 0。**如果 LLM 改写了措辞（哪怕意思一样），这条就红。** 所以实现上应做「引用式生成」而非「自由生成」。

> 这条判据很严——严格到可能逼我们放弃在紧急模式用 LLM 改写，只做模板填充。**这是刻意的**：紧急场景下措辞差异会改变人做的事，宁可句子生硬，不许句子漂亮但不准。

### 5.4 触发条件

RAG 不是「有空就做」，按下面顺序：

1. M1 交互链路验收通过（`09-M1-自测记录.md` 的 6 项未测补完）；
2. 剩余 7 条知识库条目至少再完成 3 条（RAG 需要足够语料才有意义，3 条场景不需要向量检索）；
3. 拿到大模型 API key 与计费预算；
4. 先做**离线可回归的评测集**：把 `09` 里的 20 条库内 + 20 条库外扩到 100 条，作为换 RAG 前后的对照组。**没有对照就不换**，否则无法证明「更灵活」不是「更爱编」。
