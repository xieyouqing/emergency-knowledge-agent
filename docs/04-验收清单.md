### 3.1 【已修 K1】S5：播报里补上「同时拨打 N」

S5 原文（`01` §8）：

> 生命危险场景：给关键步骤 + **播报含「同时拨打 120」** + 显式拨号按钮  
> 判据：命中 `life_threatening: true` 的条目，**播报文本须含该句，缺一即失败**

逐条实测：

| 条目                 | `life_threatening` | 播报含「同时拨打」 | 播报含「120」 | 卡片号码 | 判 |
| ------------------ | ------------------ | --------- | -------- | ---- | - |
| gas_leak           | true               | ✗         | ✗        | 119  | ❌ |
| fire_home          | true               | ✗         | ✗        | 119  | ❌ |
| co_poisoning       | true               | ✗         | ✗        | 120  | ❌ |
| electric_shock     | true               | ✗         | ✗        | 120  | ❌ |
| airway_obstruction | true               | ✗         | ✗        | 120  | ❌ |
| earthquake         | true               | ✗         | ✗        | 119  | ❌ |

**根因**：朗读稿只拼接条目字段（S1「不许改写」），而 9 条里没有任何一条的 `steps` 含「拨打」字样。所以「播报含该句」在现有结构下无法自动成立。

**修法（用户 2026-11-19 裁决：走方案 A，号码取本条）**

| 方案                       | 判定                                                                                                                                        |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **A 播报层加固定安全句（采纳）**      | `voice.js` 新增 `composeEmergencyCallSentence()`，只在 `life_threatening: true` 时返回「同时拨打{本条 emergency_number}。」。属「怎么说」不是「说什么」，不新增任何操作指导，不违反 S1 |
| B 写进条目 `steps.immediate` | 否决：要改 9 条 JSON 并重过源文逐字比对，且源站未必这么写                                                                                                         |
| C 改 S5 判据                | 否决：违背「必须能听」初衷，只听不看的老人拿不到这个信息                                                                                                              |

**为什么不能硬写 120**：6 条生命危险条目里，燃气/火灾/地震的正确号码是 **119**，中毒/触电/气道梗阻是 **120**。统一念 120 会让消防场景拨错号。用户裁决取本条号码。

**位置**：步骤稿放在「绝对不要做」之后（不在开头——老人最先要听「立刻做什么」）；分诊稿放在选项之后（顺序反了会让人以为不用回答分诊问题）。

**实测生成的朗读稿**（`gas_leak`，2026-11-19 跑出来的原文）：

```
燃气泄漏。立刻做。打开所有门窗通风。关掉燃气灶和总阀门。离开屋子，到室外去。
接着做。在室外联系燃气公司报修。情况严重就在室外打 119。
绝对不要做。不要开灯或关灯。不要使用明火、不要打火机试漏。关阀后仍有浓味就别回屋。
同时拨打119。
```

**S1 反向断言的连带修正**：原断言「朗读稿剥掉条目字段后只剩标点」会因这句合规安全句误报。  
改为先剔除 `composeEmergencyCallSentence()` 的结果再判——S5 是唯一允许的例外，且由另一条正向断言单独检查它必须存在。

**U8 静默段实测**（2026-11-19，`tools/probe/u8_probe.html`，hook `TTS.speak` 记调用次数）

| 步 | 动作 | 预期 | 实测 |
|---|---|---|---|
| 1 | 点图标 → 出分诊卡 | 自动读 1 次 | **1 次** ✓ |
| 2 | 点「停止」 | `autoRead.muted = true` | **true** ✓ |
| 3 | 按停后**同一流内**选分诊选项 → 出步骤卡 | 不读（0 次） | **0 次** ✓ |
| 4 | 手动点「朗读一遍」 | 出声（不受静默限制） | **1 次** ✓ |
| 5 | 新一次提问（点另一场景图标） | 解除静默并出声 | **1 次 + muted 变 false** ✓ |

**为什么第 3 步这样设计**（这是本轮最容易写错的地方）：
「按停后不再自动读」**只在同一次提问流内成立**。点图标按设计就是「新一次意图表达」，会解除静默。
若把第 3 步写成「按停后点另一个图标」，测的其实是「解除静默」，与 U8 判据不是一回事——首版就写错了，已改。

**顺带发现一个可观测性缺口（不影响功能，记录备查）**：
`app.js` 里所有 `V.speak(...)` 调用都是 `{ force: true }`，**没有一处传 `auto` 标记**。
`isAuto` 只在 `speakSteps` 内部用于「是否弹错误提示」，没有透传给 TTS。
后果：日志里分不清「自动读」和「手动读」，也算不出自动读失败率。**不属于 M2 阻断项**，已记入待办。

## 7. F 组：模型能力边界与待验项（区分性质，不许混）

**先分清三类，混在一起会导致两种错误**：把模型能力当成自己的验收项 → 永远过不了的假门槛；
把该验的也推给模型 → 真问题没人管。

| 类 | 内容 | 谁来负责 | 在本清单里的地位 |
|---|---|---|---|
| **甲** | 云 ASR 模型本身的识别能力（噪声、方言、口音） | 上游模型厂商 | **不是验收项**，是「对外不许宣称的边界」（§7.1） |
| **乙** | 我们自己的链路指标（时延、兜底、失败提示） | 我们 | **是验收项**（§7.2） |
| **丙** | 属其它里程碑或环境准备 | M3 / 演示前 | 移出 M2 或单列（§7.3） |

### 7.1 甲类：模型能力边界（不是验收项，是对外口径的约束）

这些**我们改不了代码**，验了也不会让产品变好。但必须留一条记录，因为它们是「不能说什么」的依据。

| # | 边界 | 已知状态 | 因此**不许**对外说 |
|---|---|---|---|
| F1a | 噪声下识别率（`01` V4，60 dB） | 未测。现有 3/3 全在安静环境（TTS 合成音 + 本人朗读） | 「嘈杂环境也能用」「火场里也能说」 |
| F5 | 方言与口音 | 未测。样本全是标准普通话 | 「支持方言」「南腔北调都听得懂」 |

**为什么保留这一节而不是全删**：`docs/04` 存在的意义之一是防止虚报。
如果把 F1a/F5 删干净，任何人都可以拿「3/3 识别正确」去宣称「任何环境都能用」——
而那句 3/3 的全前提是安静环境。这不是要求我们实现什么，是要求我们**别把边界说成能力**。

### 7.2 乙类：我们自己的，必须验

| # | 待验项 | 为什么算我们的 | 怎么验 | 现在不做的影响 |
|---|---|---|---|---|
| F2 | **首句播报 ≤ 3 秒**（`01` §4.1 判据 4 硬指标） | 时延由**我们的链路**决定 | ✅ **已测（2026-11-19）**：`node tools/measure_latency.mjs` | ✅ **临界通过**，见 §7.2.1 |
| F1b | **识别失败时的兜底必须给明确提示**（不是「识别率」，是「失败了怎么告知」） | 8 类错误文案是我们写的；噪声下更容易触发，正好一并验 | 制造失败（拔网线 / 静音 / 太短 / 拒权限），看是否每类都有对应提示 | 已实现且有断言，但**未在真机逐类触发过** |

> **F1 必须拆开的理由**：识别率是模型的，兜底是我们的。
> 混成一条会导致「因为模型在噪声下不准，所以我们的兜底也不用验了」——而兜底恰恰是噪声场景最后一道防线。

#### 7.2.1 F2 实测结果（2026-11-19，两轮共 8 次）

**命令**：`node tools/measure_latency.mjs 5`
**计时口径**：`t0` = 调用 `ASR.stop()`（等价老人松手）；`t1` = `speak()` 被调用（开始播第一个字）。

| 次 | 编码+重采样（我们） | 云 ASR（上游） | 判定+拼接（我们） | **合计** |
|---|---|---|---|---|
| 1 | 11ms | 1191ms | 930ms | **2135ms** |
| 2 | 11ms | 731ms | 819ms | **1561ms** |
| 3 | 11ms | 829ms | 735ms | **1577ms** |
| 4 | 11ms | 757ms | 1040ms | **1805ms** |
| 5 | 11ms | 792ms | 1828ms | **2629ms** |
| 6–8（前一轮） | 10–11ms | 662–915ms | 680–900ms | **1516 / 1609 / 1735ms** |

**8 / 8 全部 ≤ 3000ms，最大 2629ms。**

**但这个结论必须带三条限定，否则是虚报**：

| # | 限定 | 数据 |
|---|---|---|
| 1 | **属临界通过，不是稳定通过** | 最大 2629ms，距判据仅剩 **371ms** 余量；而真实浏览器 `speechSynthesis` 出声还要再加 50–200ms |
| 2 | **判定段是最大波动源** | 735–1828ms（2.5 倍差距）。ASR 段反而更稳（662–1191ms） |
| 3 | **样本是安静环境 + 标准普通话** | 与 F1a/F5 同源限制；且 8 次是同一句话（`煤气漏了怎么办`），不是 20 次不同句子 |

**若要更稳的两条路**（未实施，属优化不属缺陷）：

| 方案 | 做法 | 收益 |
|---|---|---|
| A 先播已确定的 | `detectDanger()` 是本地毫秒级。命中危险信号时先播「{场景名}。同时拨打N。」，LLM 判定回来再补读步骤 | 首句可压到 200ms 内，且不受判定波动影响 |
| B 判定并行 | ASR 返回后立刻用 l3 规则出临时卡并开播，LLM 结论到了再校正 | 同类收益，但会引入「卡先出后变」，对老人不友好，**不建议** |

**上游抖动的实测记录**（必须记，否则复测时会误判成自己的 bug）：

`e2e_asr.mjs` 有一次跑到 **9477ms**（ASR 段），复查是上游网络抖动，非产品问题。
同期正常区间是 662–1191ms。因此 `e2e_asr` 里原来那条「端到端 < 8s」的断言已改为
「ASR 段 < 5000ms」——**8 秒是自造门槛，`01` 里没有这条判据**，属于把上游抖动误当产品缺陷。

**结论**：判据 4 判定为**通过（临界）**。余量不足以覆盖最坏情况（判定 2.5s + 浏览器出声 0.2s ≈ 2.7s 仍勉强），若真机复测出现 > 3 秒，应实施方案 A。

**顺带修的测试基础设施缺口**：`03` v1.7 写明「复跑评测前须清代理缓存」，但代理**没有**清缓存接口。
本轮补了 `POST /cache/clear` 与 `/judge` 的 `nocache: true` 参数——
没有它们，测量出的「判定 3ms」是缓存命中，会让人误以为链路很快（首次跑就踩了这个坑）。
