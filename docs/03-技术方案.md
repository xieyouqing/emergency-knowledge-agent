## 1. 结论先行

**M1 的字符匹配准确率 31.3%（实测 16 条错 11 条），错误全部来自「意图缺失」，不是「检索不准」。因此方案是三层流水线 + 混合检索。**

> **命名约定**：本节的三层是**处理流水线**（判定 / 检索 / 生成）。§5 的 L1/L2/L3 是**降级层级**（联网精排 / 无精排 / 字符检索）。两者不是一回事，本文严格区分，不用同一套符号。

```
用户输入
  │
  ├─[① 判定层]── 场景 × 意图，由 LLM 输出标签（不生成内容）
  │
  ├─[② 检索层]── 混合检索：BM25(字符 bigram) + 向量 → RRF 融合
  │                 → cross-encoder 精排打分
  │                 → 阈值硬筛（不够一条都不进）
  │                 → 父文档整条注入
  │
  └─[③ 生成层]── 按权限矩阵输出：紧急只许选/排序/精简，日常可扩写

【降级层级，见 §5】L1 联网+精排 → L2 无精排 → L3 字符检索（模型全挂时）
```

**四条不可让步的设计约束**：

| # | 约束 | 违反的后果 |
|---|---|---|
| A1 | 判定层只输出**标签**，不输出文字 | 让 LLM 在判定阶段"顺便解释"，等于把幻觉注入路由 |
| A2 | 检索命中后注入**父文档整条**，不做片段拼接 | 命中「打 119」却没注入「不要开灯」→ 步骤不完整 |
| A3 | 阈值不够时**一条都不进**，不许"凑一条最像的" | 凑出来的那条就是编造的入口 |
| **A4** | **精排分数只用于排序与相对比较，不单独用作绝对阈值** | cross-encoder 分数不可跨 query 比较，拿它卡固定阈值会误杀（依据见 §3.5） |
| **A5** | **任何降级层级都不得静默**，L3 必须显式提示且不可关闭 | 用户以为得到完整能力，实际是精度最低的一层（依据见 §5.4） |

## 2. 判定层：场景 × 意图二维

### 2.1 为什么必须二维（实测依据）

`node tools/probe_retrieval.mjs` 用 16 条用例探测当前字符匹配：

| 组 | 语义 | 正确 / 错误 | 错例 |
|---|---|---|---|
| A 真紧急 | 正在出事 | **4 / 0** | — |
| B 预防咨询 | 问知识 | **0 / 4** | 「怎么预防煤气泄漏」→ 强制切紧急 |
| C 含词无关 | 不归我管 | **1 / 7** | 「电梯广告怎么投诉」→ 进电梯困人 |

**关键观察**：这 11 条错例的**场景判定全部正确**——「怎么预防煤气泄漏」确实在说燃气泄漏。错在第二维：它不是在出事，是在问知识。

> 单纯换检索算法**解决不了**这个问题。「怎么预防煤气泄漏」与「煤气泄漏了」共享全部关键词，向量距离极近，混合检索也一样分不开。**意图维度无法由检索替代。**

### 2.2 输出契约

**一次 LLM 调用，只输出结构化标签**：

```json
{ "scene": "gas_leak", "intent": "ongoing", "confidence": 0.0 }
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `scene` | 注册表 slot id 或 `null` | 必须命中 `index.json` 白名单，越界视为 `null` |
| `intent` | `ongoing` / `prevention` / `off_scope` | 三值，不允许第四种 |
| `confidence` | 0–1 | 低于阈值不猜，见 §3.5 |

**A1 的落地方式**：prompt 明确禁止输出任何自然语言解释，只允许 JSON。解析失败一律按 `scene: null, intent: off_scope` 处理——**判不出来就当拒答，不许猜**。

### 2.3 三值语义

| `intent` | 含义 | 判例 |
|---|---|---|
| `ongoing` | 事情正在发生，用户要行动 | 「煤气漏了」「我妈摔倒了起不来」 |
| `prevention` | 事情没发生，用户要知识 | 「怎么预防煤气泄漏」「家里要不要装报警器」 |
| `off_scope` | 与该场景无关，或完全不归我管 | 「煤气费怎么交」「今天天气怎么样」 |

### 2.4 语音通道（M2，2026-11-18 新增）

`01` §2.1 定「语音播报是主输出通道，文字只是备份（M2 起生效）」。本节记录实现与三条平台事实。

#### 2.4.1 三个必须知道的平台事实

**事实 1：Android WebView 不支持语音识别（SpeechRecognition）**

> 来源：Chromium Blink-dev「Intent to Ship: SpeechRecognitionResult Timestamps」｜https://groups.google.com/a/chromium.org/g/Blink-dev/c/X-mFPzgH6Os ｜获取 2026-11-18
> 原文：「The Web Speech API (SpeechRecognition) is **not supported on Android WebView**」「Android WebView does not support the SpeechRecognition API, and Chrome on Android delegates to the OS-level Android SpeechRecognizer service」

**后果**：D-3 那个「一套代码覆盖三产物」的假设，在**语音输入**上不成立。桌面浏览器能用 `SpeechRecognition`，Tauri APK 里的 WebView 不能。这是 M2-ASR 的核心约束，见 §2.4.3。

**事实 2：微信内置浏览器对 Speech API 支持极差**

> 来源：TNotes.javascript《Speech Synthesis 与 Speech Recognition》｜https://tnotesjs.github.io/TNotes.javascript/notes/153 ｜获取 2026-11-18
> 原文：「微信内置浏览器和支付宝内置浏览器对 Speech API 的支持非常有限或完全不支持」
> 证据级：**引用（第三方技术笔记，非官方）**，标为推断依据，不作定论。

**后果**：若产品靠微信传播，网页版在微信内**不能作为语音入口**。这一点在 §6.6.4 的 WASM 实测里是反面情形——那个场景微信内核表现很好，语音场景则不可依赖。**同一个容器，两种能力，不能一概而论。**

**事实 3：TTS 有跨平台方案，Android 走原生 TextToSpeech**

> 来源：tauri-plugin-tts v0.1.12 文档｜https://docs.rs/crate/tauri-plugin-tts/0.1.12 ｜获取 2026-11-18
> 原文：「Platform Support: Windows ✅ Full support (SAPI) / macOS ✅ Full support (AVSpeechSynthesizer) / iOS ✅ Full support (AVSpeechSynthesizer) / **Android ✅ Full support (TextToSpeech)**」
> 同页明确 Android 的坑：「**Voices needing an uninstalled language pack are filtered out of `getVoices()`, so an empty list usually means nothing is downloaded**」

**注意这是社区插件**（`armelhbobdad/tauri-plugin-tts`），不在 Tauri 官方 `plugins-workspace` 内。用它需接受维护风险；备选是自己写一层 Kotlin 桥（V9 的工作量估算待更新）。

**事实 3 恰好印证了 `01` §6.2 定的原则**：插件缺语音包时**不报错，只返回空列表**。所以「启动即检查中文可用性」必须我们自己做，不能指望库报错。

**事实 4：Android 手机浏览器（非微信）同样没有 `speechSynthesis`**

> 来源：`tools/probe/tts_probe.html` 真机探测（2026-11-18，小米 Android 16，浏览器标识 AppleWebKit，非微信内，http 页）
> 探测结果：`speechSynthesis` 存在性 = **无**；探测页判定「这台设备的浏览器不支持语音朗读」

**后果**：事实 2 原本只否定「微信内网页」，事实 4 把范围扩大——**Android 上任何浏览器路径都不能依赖语音输出**。`voice.js` 的 ② web 层在 Android 上会落到 ③ none（文字 + 明确提示，不静默失败）。Android 的语音输出只剩 ① tauri-plugin-tts（系统原生 TextToSpeech）一条路，M3 打包后才能实测（V8 剩余部分）。桌面浏览器不受影响。

#### 2.4.2 实现：三层自动选择

```
TTS.detect()
   │
   ├─ ① tauri  Tauri 环境 + tauri-plugin-tts → 原生 SAPI / Android TextToSpeech
   │           （需 npm install tauri-plugin-tts-api；本仓库暂未装，走 ②）
   ├─ ② web    window.speechSynthesis 且**有中文音色**
   │           （桌面可靠；Android 浏览器不可依赖——事实 4）
   └─ ③ none   都没有 → 返回 unavailableReason，界面显示提示
```

**为什么 ② 要额外检查「有中文音色」**：有 `speechSynthesis` 不等于能读中文。设备只装了英语音色时，引擎会把中文按外文念或直接无声，**但不报错**。若只看 API 是否存在就判「可用」，用户会看到「朗读按钮能点、点了没反应」——正是 §06.2 禁止的静默失败。

**朗读稿的拼法（S1 约束）**：`composeStepsScript()` 只做三件事，**不改写任何文字**：

| 做什么 | 为什么 |
|---|---|
| 念出段落标题（「立刻做」「接着做」「绝对不要做」） | 让听的人知道换段了 |
| 每条步骤后加句号 → 产生停顿 | 否则连成一串听不清 |
| 禁忌段前缀整段念出 | 只念「不要开灯」容易漏听「不要」 |

断言方式不是「听着对」，而是**「稿子剥掉所有条目字段后必须只剩标点」**——这是能失败的判据。

**分诊覆盖**：用户在分诊卡选了「还有很浓的味」后，朗读必须读 override 的步骤，不能读默认步骤。读错指导比不读更危险。

#### 2.4.3 自动朗读（2026-11-18，用户裁决 B）

`01` §2.1 说「语音播报是主输出通道」——既然是主通道，就不能要求老人先找到按钮再点。所以出卡片即自动朗读。

**四条边界，每条都能写成断言**：

| 规则 | 理由 | 断言 |
|---|---|---|
| **步骤卡只在紧急模式自动读** | 日常模式用户点「查看操作步骤」是在看清单，可能只想扫一眼，被念一长段步骤会打扰 | 日常模式渲染步骤卡 → 发声次数不变 |
| **日常解释卡自动读，但只读「名称 + 摘要」一句** | 见 §2.4.3-b：打字提问出的就是这张卡，不读等于「打字不响」，而打字才是真实用法 | 渲染日常卡 → 发声一次，且不含 `why` 与 `prevention` 清单 |
| **自动读失败必须静默** | 浏览器自动播放策略可能拦截（无用户手势）。此时弹「朗读失败」只会让人困惑——用户根本没主动要求朗读 | 失败不插提示条；手动按钮始终是可靠路径 |
| **按过「停止」= 本会话不再自动读** | 自动朗读按了停还继续读，等于用户说「别念了」而系统不听 | 置静默后渲染新卡（步骤卡与日常卡）→ 发声次数不变 |

**一个必须处理的例外**：**新一次提问或点图标会解除静默。** 否则老人按过一次停止，后面所有场景就再也听不到声音，而他根本不知道为什么。手动点「朗读一遍」也不受静默限制。

#### 2.4.3-b 日常解释卡为什么也要读（2026-11-18 实测修正）

**发现**：v1.0 只把自动读挂在步骤卡上（`renderStepsCard` 三处）。真机/预览实测反馈：**点图标会读，打字提问不读**——因为打字出的多是日常解释卡（`renderDaily`），而那张卡连朗读按钮都没有。

**这不是 bug，是当初的边界选错了参照物**：定边界时假设「打字提问 ≈ 紧急求助」，实际老人打字问的多是「怎么预防燃气泄漏」这类知识问题，恰好落到只读的那张卡上。点图标会读只是**演示路径**，不能代表产品可用。

**修正后的边界**（用户裁决：只读名称+摘要）：

| 卡型 | 自动读什么 | 手动「朗读一遍」读什么 |
|---|---|---|
| 步骤卡（紧急模式） | 名称 + 三段步骤全文 | 同左 |
| 分诊卡 | 名称 + 问题 + 选项 | 同左 |
| **日常解释卡** | **名称 + `daily.summary` 一句** | 名称 + 摘要 + `daily.why`（`composeDailyScript`） |
| 拒答卡 / 拨号卡 | 不读 | 无按钮（没有说话内容，S1） |

**为什么日常卡只读摘要**：全文（摘要+原因+「平时怎么做」四条+误区）念完约 40–60 秒。老人的反应是**按停止**，那就等于没读。一句摘要能让他判断「这事跟我有没有关系」，要不要听全文由他自己点。

**顺带修的缺陷**：语音不可用提示原来固定插进 `el.emgAnswer`，日常模式下那块是隐藏的——提示插进去等于没提示（违反 §6.2 不许静默失败）。改为按当前 `state.mode` 选容器。

**分诊卡阶段读什么**：此时还没有步骤，只能读「问题 + 选项」。

```
「煤气漏了」→ 燃气泄漏。关掉总阀门以后，还能闻到很浓的味道吗？
             第1个，还有很浓的味。第2个，味小了或没有了。
```

**为什么不能直接读默认步骤**：用户还没回答分诊问题，读默认步骤等于给了他一条可能不适用的指导（比如「关阀后仍有浓味」的人应该立刻撤离，而不是留在室内通风）。**读错指导比不读更危险。**

选择分诊选项后，自动朗读切换到对应的 `override` 步骤。

#### 2.4.4 语音输入（ASR，M2 已实现 2026-11-19）

**结论先行：不走 Web Speech API，走「自己录音 + 上传云 ASR」。**

| 平台 | Web Speech API（`SpeechRecognition`） | 本方案（录音 + 云 ASR） |
|---|---|---|
| Windows 桌面 | 可用 | **可用（已实测）** |
| Android 浏览器 / WebView | **不支持**（事实 1） | 录音可用；识别靠云端，**与平台无关** |
| 微信内网页 | 基本不可用（事实 2） | 录音受安全上下文限制，同左 |
| M3 打包后 | 依赖 WebView 能力 | **联网可用**（走 D-7 云端中继，key 在服务端）／**断网不可用**（云端能力的物理边界，D-6 两态表） |

**为什么换路线的直接理由**：事实 1/2 让 Web Speech API 在 Android 上整体不存在。而「录音 + 上传」只需要 `getUserMedia`（跨平台一致）和一次 HTTP 请求，把平台差异全部消掉。

**实测（2026-11-19，DeepSeek `/v1/tools/asr`）**：

| 项 | 值 |
|---|---|
| 端点 | `POST https://api.deepseek.com/v1/tools/asr` |
| 字段名 | `file`（`multipart/form-data`） |
| 返回 | `{"text":"煤气漏了怎么办？","duration_ms":1680,"latency_ms":992}` |
| 1.6s 中文语音 | 墙钟 891 / 936 / 992 / 1328 ms（多次） |
| 识别正确性 | 「煤气漏了怎么办」「怎么预防燃气泄漏」「今天天气怎么样」**3/3 全对** |
| 12MB 上限 | 约 6 分钟 16k 单声道 WAV |

**闭环验证方法**（不依赖真人录音，可重复）：用同一 API 的 `POST /v1/tools/tts` 合成目标句子 → 把音频交给 ASR → 比对文本。脚本：`tools/e2e_asr.mjs`。

#### 2.4.5 录音与编码（`app/asr.js`）

```
按住 ──► getUserMedia ──► AudioContext(48k) ──► ScriptProcessor 收 PCM
                                                      │
松手 ──► 重采样到 16k（线性插值）──► 编码 WAV(PCM16 单声道) ──► POST 代理 /asr
                                                      │
代理 ──► 组 multipart ──► DeepSeek /v1/tools/asr ──► {text} ──► handleQuery
```

**五个不能省的细节，每个都有对应断言**：

| 细节 | 为什么 | 断言 |
|---|---|---|
| 目标采样率 **16000** | 端点实测这个率最稳；改动必须重测识别质量 | 重采样后 1 秒 = 16000 点 |
| `inputBuffer` 必须**复制** | 它是复用缓冲，存引用会拿到全 0 | （实现层，见代码注释） |
| WAV 头逐字段正确 | 头错 → 端点返回空文本，而不是报错（静默失败） | RIFF/WAVE/fmt/PCM/单声道/16000/16bit/长度字段 8 条 |
| 满幅钳位 | 超过 ±1 的信号溢出会变成反相噪声 | `1.0 → 32767`、`-1.0 → -32768`、`2.0 → 32767` |
| `touch-action:none` | 否则按住时页面跟着滚，录音被中断 | CSS 声明存在 |

**为什么不用 `MediaRecorder`（webm/opus）**：体积小 10 倍，但**没验证过端点是否接受**，失败就得返工。WAV 已实测可用，且编码只 42 行。老人一句话 3–5 秒 ≈ 100KB，体积不是问题。

#### 2.4.6 语音输入的兜底（错误必须分类）

**不许把六种失败合并成一句「识别失败」**——老人无法据此做任何事。

| 失败 | 原因 | 用户看到的话 |
|---|---|---|
| 非安全上下文 | `file://` 双击打开 | 「语音输入需要先启动本地服务（localhost 或 https）」 |
| **`SecurityError`** | 页面被嵌在 iframe 里且未授予 `microphone` 权限（**WorkBuddy 预览面板即属此类**） | 「页面被嵌在其他窗口里……请在新标签页里打开」 |
| 无 `getUserMedia` | 旧浏览器 | 「这台设备的浏览器不支持录音」 |
| 权限被拒 | `NotAllowedError` | 「请在浏览器地址栏允许使用麦克风」 |
| 无设备 | `NotFoundError` | 「这台设备没有找到麦克风」 |
| 设备被占用 | `NotReadableError` | 「麦克风被别的程序占用了（比如正在打电话）」 |
| 录音太短 | < 400ms | 「说话时间太短了，请按住多说两个字」 |
| 识别为空 | 端点返回 200 但 text 空 | 「没有听清。请靠近一点，按住按钮再说一遍」 |
| 网络失败 / 超时 | 代理没起 / >15s | 「连不上识别服务」/「识别太慢了」 |

**识别结果：填进输入框 + 立即出答案（一步，不需要再点确认）。**

两次用户实测共同定下这条，缺一不可：

| 用户原话 | 推出的要求 |
|---|---|
| 「你是不是没有连接文本框？问了也没用」 | 识别文本**必须可见**（写进输入框） |
| 「做成输入后直接出答案，不需要再确认」 | **不要**多一步点击（识别完直接 `handleQuery`） |

两者不冲突：**同一时刻做两件事**——填框（让人看得见、能改、能重说）+ 立即出答案。

| 设计点 | 说明 |
|---|---|
| 填框是「给人看的」，不是「等人确认的」 | 老人要能核对系统把他的话听成了什么 |
| 出答案不等确认 | 语音的价值是「不用动手」，加一次点击就把这个价值抵消了 |
| 填框失败不阻断出答案 | 界面结构变了（拿不到 input）时仍要出答案，绝不吞掉识别结果 |
| 识别为空或失败时，输入框保持原样 | 不清空用户已经输入的文字 |

**与打字走同一个入口**：最终都调 `handleQuery`，不另开一套逻辑，
否则语音路径会慢慢和文字路径行为不一致（B4 那次 bug 的形状）。

## 3. 检索层：混合检索 + 父子文档

### 3.1 三级结构（「文档过长」的结构性解法）

> **命名约定**：文档层级用 **D0 / D1 / D2**（D = Document）。降级层级用 L1 / L2 / L3（见 §5）。不要混用。

| 级 | 名称 | 是否入库 | 是否注入 context | 用途 |
|---|---|---|---|---|
| **D0** | 原始网页全文 | **否** | **否** | 只存 `source.url` + `source.quote`，供机器比对与人工回溯 |
| **D1** | 父文档 = 一条 entry 的结构化字段 | 是 | **是，整条** | 注入单元 |
| **D2** | 子块 = entry 内的语义切片 | 是（构建期生成） | 否 | 检索单元 |

**为什么「文档内容过长」在现有架构下已结构性解决**：真正长的是 D0（网页原文，可能几万字），它**从不进 context**；D1 是一条 entry 的结构化字段，量级 1–3KB。父子关系是 D2 → D1，不是「长文档切成块」。

> **未来扩展点（现在不做）**：若某场景要挂多份独立长文档（如《老年人跌倒干预技术指南》全文），D1 会膨胀为「一个场景的文档集合」，届时需插入 D1.5「文档级父节点」。触发条件：单场景 D1 字段总量 > 8KB，或挂载文档数 ≥ 3。

### 3.2 D2 子块的切分规则（硬约束）

| 子块 | 包含字段 | 检索作用 |
|---|---|---|
| `c1` 场景识别块 | `name` + `aliases` + `keywords` | 回答「用户在说哪件事」 |
| `c2` 处置块 | `steps.immediate` + `steps.next` + **`steps.never`** | 回答「现在该做什么」 |
| `c3` 日常块 | `daily.summary` + `why` + `prevention` + `misconception` | 回答「为什么 / 怎么防」 |

**三条切分硬规则**：

| # | 规则 | 理由 |
|---|---|---|
| S1 | **`steps` 三段必须同属一个子块，`never` 永不单独成块** | 若 `never` 可被独立检索，会出现「只命中禁忌段」→ 注入一堆「不要做」而没有「该做什么」。更糟的是 LLM 只看到禁忌段时倾向自行补全动作 |
| S2 | **子块不得跨 entry 拼接** | 跨条目拼接等于制造知识库里不存在的组合，违反 S2（可回溯） |
| S3 | **切分点只在字段边界，不在句子中间** | 中句子切断会破坏「一个动作只写一件事」的语义（契约 §4.4） |

> **这是「父子文档」与普通 RAG 分块的最大区别**：普通 RAG 按固定 token 数切，切到哪算哪；我们的切分点是**数据契约规定的字段边界**，切出来的块天然带语义标签。

### 3.3 混合检索：BM25 + 向量 + RRF

**为什么必须混合**（两条路各有一个致命短板）：

| 方式 | 强项 | 短板 | 本项目实例 |
|---|---|---|---|
| **BM25**（稀疏 / 词面） | 专有名词、数字、短词精确命中；零模型、零延迟、完全可解释 | 同义表达完全不命中 | 问「煤气漏了」，文档写「燃气泄漏」→ BM25 可能 0 命中 |
| **向量**（稠密 / 语义） | 同义、近义、换说法都能命中 | 对「119」「燃气阀门」这类具体词不敏感；可能被高频无义词带偏 | 问「电梯广告怎么投诉」，与电梯困人向量距离近 → 误召 |

**两者错的地方不重叠，所以融合有效。**

#### 3.3.1 BM25 的中文实现：字符 bigram，不引入分词词典

| 项 | 决定 | 理由 |
|---|---|---|
| 分词 | **字符 bigram**（「煤气漏了」→ `煤气 / 气漏 / 漏了`） | 中文无空格；用词典分词要引依赖 + 词典体积 + 新词失效（「燃气阀门」可能切错）。bigram 对中文短文本检索有效且**零依赖、零词典** |
| 参数 | `k1 = 1.2`，`b = 0.75`（BM25 通用默认值） | 语料只有几十条时参数不敏感，不做调参 |
| 停用字 | 去掉「的/了/吗/怎/么」等高频虚字 bigram | 否则「怎么」在几乎每个 query 里都出现，稀释信号 |

**为什么不用 jieba 等分词器**：前端是纯 JS，引分词器等于引词典文件 + 增加构建复杂度；而本项目查询以 5–15 字短句为主，bigram 完全够用。**这是「引入依赖必须换来当前无法实现的能力」规则的具体应用——分词换不来什么。**

#### 3.3.2 融合：RRF，不做加权求和

```
BM25 ranking  ──┐
                ├─→ RRF 融合 ─→ 候选集 (top-20)
向量 ranking  ──┘
```

**RRF（Reciprocal Rank Fusion）**：

```
score_RRF(d) = Σ_over_retrievers  1 / (k + rank_i(d))      k = 60
```

| 为什么不加权求和 | 说明 |
|---|---|
| 分数尺度完全不同 | BM25 是 0–20+ 的无界分，余弦相似度是 -1–1。直接相加必须归一化 |
| 归一化不稳定 | min-max 归一化依赖当次候选集分布，换一个 query 分布就变，同一文档分数会漂移 |
| RRF 只用排名 | 免归一化，对尺度免疫，实现 20 行代码，被广泛验证 |

**代价（必须承认）**：RRF 丢弃了分数绝对值，只用相对排名。所以**它无法直接回答「这个文档到底够不够相关」**——这正是必须再加一层精排的原因。

#### 3.3.3 召回数量

| 项 | 值 | 理由 |
|---|---|---|
| 每路召回 | top-10 | 子块总量预计 30–300 个，取 10 已覆盖 3%–30% |
| RRF 融合后 | **top-20** 进精排 | 精排是 cross-encoder，逐对推理，20 对是延迟与召回率的平衡点 |
| 精排后 | **top-3** 且过阈值 | 与用户要求一致（top-3 → 整条注入） |

### 3.4 精排：cross-encoder 打分

**由用户指定的「给问题和文档的相关度打分」环节。**

| 项 | 说明 |
|---|---|
| 模型类型 | cross-encoder（query 与 doc **联合**编码，直接输出一个相关度 logit） |
| 与双塔的区别 | 双塔（embedding）分别编码后算余弦，快但精度低；cross-encoder 精度高，但每对要推理一次 |
| 输入 | `(query, c2 处置块)`、`(query, c3 日常块)` 等已召回子块 |
| 输出 | sigmoid 后的 [0,1] 分数 |
| 用途 | **只做排序 + 相对比较**（约束 A4） |

**为什么精排能救回混合检索救不回的情况**：cross-encoder 同时看到 query 和文档，能判断「怎么预防煤气泄漏」与「煤气泄漏处置步骤」**主题相同但意图不匹配**。这是它比双塔强的地方，也是本方案里唯一能部分缓解意图误判的检索侧手段。

> **但注意**：精排缓解的是「检索侧误召」，**不能替代判定层的意图分类**。用户问「怎么预防」时，精排确实会把 c3 日常块排到 c2 处置块前面——但如果判定层已经判成 `ongoing`，流程仍然会去注入 c2。**判定层的错误，检索层补不回来。**

### 3.5 阈值：「一条都不进」怎么落地

> **v0.3 起的前提**：D-2 裁决为「reranker 不内置」（§3.6.3），因此**精排只在联网时可用**。阈值必须按链路分开维护（v0.4 起为三套：L1 精排 / L2 余弦 / L3 字符规则分，见下表）。**各套分数尺度不同，分别标定，不可互相套用。**

#### 3.5.1 关键风险：精排分数不可跨 query 比较

> **来源（引用，非实测）**：掘金《本地 266MB 模型，追平大模型 API》（见 §3.6 数据表）
> 原文摘录：「同一个 refund-policy.md，两条不同的问题分别打到 0.222 和 0.869。所以不要用固定阈值判断『资料是否充足』。0.222 不代表文档无关，只代表这条问法下它排得低。如果你的系统里写了 `if (score < 0.5) return "资料不足"`，这条规则是错的。」
> 获取日期：2026-11-18

**这意味着**：直接写 `if (rerank_score < 0.5) 拒答` 是错的。同一个相关文档，换个问法可能从 0.87 掉到 0.22。

**因此阈值必须分层，且精排分数不单独作绝对判据**（约束 A4）。

#### 3.5.2 三套阈值链路（对应 §5 的三层兜底）

> **v0.4 变更**：D-2 = B 使精排只在联网时可用；用户裁决三层兜底使 L3 用字符检索。因此阈值共**三套**，尺度互不相通。

**L1 链路（联网 + 精排可用）**：

| 层 | 判据 | 分数来源 | 类型 |
|---|---|---|---|
| **① 粗筛** | RRF 后是否存在候选 | RRF 排名 | 布尔 |
| **② 相对筛** | `top1 - top2 ≥ δ_rerank` 或 `top1 / 其余 ≥ ρ_rerank` | **精排分数** | 相对 |
| **③ 绝对筛** | `top1 ≥ τ_rerank` | **精排分数** | 绝对（按模型标定） |

**L2 链路（断网，或精排不可用）**：

| 层 | 判据 | 分数来源 | 类型 |
|---|---|---|---|
| **① 粗筛** | RRF 后是否存在候选 | RRF 排名 | 布尔 |
| **② 相对筛** | `top1_rrf - top2_rrf ≥ δ_rrf` | **RRF 分数** | 相对 |
| **③ 绝对筛** | `cosine_top1 ≥ τ_vec` | **向量余弦相似度** | 绝对（按 embedding 模型标定） |

**L3 链路（embedding 启动失败 → 字符检索）**：

| 层 | 判据 | 分数来源 | 类型 |
|---|---|---|---|
| **① 粗筛** | `scoreEntry()` 的最高分 `top > 0` | 离散规则分 | 布尔（**唯一自带绝对判据的一条**） |
| ~~② 相对筛~~ | **不需要** | — | — |
| ~~③ 绝对筛~~ | **已并入 ①** | — | — |

**为什么 L3 不需要第二、三层判据**：`scoreEntry()` 输出离散值（alias 10 / name 9 / keyword 4+k / 未命中 0），`top > 0` 本身就是「规则命中」这个明确事实，不是「相似度够不够」的估计。**离散判据不需要再用相对比较兜底。**

**为什么 L2 的绝对筛必须用余弦，不能用 RRF**：

| 分数 | 能否做绝对阈值 | 原因 |
|---|---|---|
| RRF 分数 | **不能** | 它只是 `1/(60+rank)` 的和。若只召回一路，top1 恒为 `1/61 ≈ 0.0164`；若两路都命中且都排第一，恒为 `2/61 ≈ 0.0328`。**值与内容无关，只与排名和路数有关** |
| BM25 分数 | **不能** | 无界且依赖语料平均长度，换一批文档分布就变 |
| **余弦相似度** | **能，但需按模型标定** | bge 系列输出分布相对稳定，同一模型下「相关 / 不相关」有可分离区间 |
| **字符规则分** | **能**（仅 L3） | 离散规则命中，无分布假设 |

> **这是 D-2 = B 带来的最重要技术后果**：L2 唯一可做绝对判断的分数是余弦相似度，所以 `τ_vec` 必须单独标定，**与 `τ_rerank` 不可互相换算**。

#### 3.5.3 三层关系与分流

**三层关系**：① 不通过 → 零命中；② 不通过 → **按 mode 分流**（见下）；③ 不通过 → 零命中。

**② 不通过时的分流**：

| 模式 | ② 不通过（分数都差不多） | 理由 |
|---|---|---|
| 日常 | **按零命中处理** → 拒答 | 分不清就是不该答。此时答错的代价高于不答 |
| **紧急** | **取 top1 注入，但同时显示拨号卡** | 正在出事时，「宁可多给一条可能有用的步骤」+「随时可拨号」比「礼貌地拒绝」安全。**这是唯一允许绕过相对筛的地方，且必须叠加拨号入口** |

#### 3.5.4 标定方法（L1 / L2 分别标，L3 无需标定）

**共同步骤（仅 L1 / L2 适用）**：

| 步 | 动作 |
|---|---|
| 1 | 标注集：40 条 query（20 正 / 20 负），人工标 `expect_scene` |
| 2 | 对每条算 top-1 与 top-2 的分数（按链路取对应分数类型） |
| 3 | 扫 τ × δ，记录每个组合的误纳率 / 误拒率 |
| 4 | 取**误纳率 = 0 前提下**误拒率最低的组合 |
| 5 | 换 embedding 模型 → 重标 `τ_vec`；换 reranker 模型 → 重标 `τ_rerank` / `δ_rerank`。写进 `manifest`，旧值作废 |

| 链路 | 标定产物 | 扫描范围 |
|---|---|---|
| **L1 联网** | `τ_rerank`、`δ_rerank`、`ρ_rerank` | τ：0.10–0.95 步长 0.01；δ：0–0.5 步长 0.01 |
| **L2 断网** | `τ_vec`、`δ_rrf` | τ_vec：0.30–0.90 步长 0.01；δ_rrf：按 RRF 量级取 0–0.02 步长 0.001 |
| **L3 字符检索** | **无产物** | 判据是 `top > 0`，**没有可调参数，也不需要标定** |

**为什么误纳率优先为 0**：误纳 = 把不相关内容当答案注入 = 编造入口；误拒 = 少答一次，用户还能点图标或拨号。**代价不对称，宁拒勿纳。**

**已知代价（必须写明）**：三条链路的判据尺度不同，**同一个问题在不同层级可能得到不同结果**（L1 答得出、L3 答不出，或 L3 误答而 L1 正确拒答）。这不是 bug，是能力差异的如实反映。但**界面必须让用户知道当前在哪一层**：

| 层 | 界面提示 |
|---|---|
| L1 | 无提示（正常态） |
| L2 断网 | 顶部「当前离线 · 数据版本 YYYY-MM-DD」（`01` §4.3 第 7 条） |
| L2 精排不可用 | 顶部「**精排不可用，结果精度下降**」 |
| **L3** | 顶部「**当前为基础模式，语义检索不可用**」，**不可关闭**（§5.4） |

#### 3.5.5 零命中分支

| 模式 | 零命中时 | 依据 |
|---|---|---|
| 日常 | 固定拒答话术 + 拨号按钮 | S1 / S4 |
| **紧急** | **拨号专用卡**（「我不编步骤，请先打电话」+ 号码），**不给拒答话术** | 正在着火的人看到「我只会答应急知识」是废话 |

**两条必须记住的结论**：

1. **BM25 是唯一完全无依赖的检索方式**——纯计算，无模型、无网络。这是它必须存在的第二个理由（第一个是补向量的词面短板）。

## 4. 生成层：权限矩阵

| 模式 | LLM 权限 | 判据（可失败） |
|---|---|---|
| **紧急** | 只许**选择、排序、精简**原文。不得新增句子 | 抽 20 条，逐句在父文档 `steps`/`never` 里逐字查找，找不到的句子数须为 **0** |
| **日常** | 可基于 `daily` 扩写解释。但**操作动作必须全部来自 `steps`/`never`** | 抽 20 条，逐句标注操作动作来源，库外动作数须为 **0**（S7） |

## 5. 降级路径：三层兜底

> **v0.4 裁决（用户）：三层兜底。两个模型（embedding / reranker）都启动失败时，退字符检索。**
> 本节的 L3 即 M1 已实现的 `detectDanger()` + `scoreEntry()`，**不是新写的代码，是保留不删的既有能力**。

### 5.1 三层定义

| 层 | 触发条件 | 检索 | 意图判定 | 绝对阈值 | 输出行为 |
|---|---|---|---|---|---|
| **L1** | 联网 + embedding 正常 + 精排可用 | BM25 + 向量 + RRF → 云端精排 top-20 → top-3 | LLM 二维判定 | `τ_rerank` + `δ_rerank` | 正常输出 |
| **L2** | 断网，或精排不可用（embedding 仍正常） | BM25 + 向量 + RRF | LLM 不可用则关键词 | `τ_vec` + `δ_rrf` | 正常输出 |
| **L3** | **embedding 启动失败**（模型损坏 / 量化不兼容 / WASM 加载失败 / 内存不足） | **字符检索**（`scoreEntry`）+ 关键词判定 | 关键词（`DANGER_RULES`） | **离散规则分 `top > 0`** | 正常输出 + 顶部降级提示 |

**「精细度递减、可用性不降」是这三层的设计目标**：任何一层都能出步骤卡，没有「什么都搜不到」的空白状态。

### 5.2 为什么 L3 用字符检索而不是纯 BM25（这是用户方案比我上一版更严谨的地方）

我 v0.3 写的是「BM25 失败 → 不自动注入，改图标区」。**那个方案有缺陷，已废弃。** 原因：

| 分数 | 能否做绝对判据 | 说明 |
|---|---|---|
| BM25 分数 | **不能** | 无界，且依赖语料平均文档长度。换一批文档，同一分数的含义就变。**没有客观的「过 / 不过」界线** |
| RRF 分数 | **不能** | 只是 `1/(60+rank)` 的和，与内容无关（只召回一路时 top1 恒为 0.0164） |
| 余弦相似度 | 能，需按模型标定 | 需要模型可用 —— 而 L3 的前提正是模型不可用 |
| **字符检索规则分** | **能** | `scoreEntry()` 输出离散值：alias 命中 10 / name 命中 9 / keyword 命中 4+k / 未命中 0。**`top > 0` 就是「命中」，`top == 0` 就是「未命中」——判据与内容语义直接对应，不依赖任何分布假设** |

**结论**：L3 必须有绝对判据，而三层里唯一自带绝对判据的是字符检索。**所以 L3 只能是字符检索，不能是纯 BM25。**

> 这个结论修正了我 v0.3 的一处错误判断。当时我认为「没有绝对阈值就只能退回图标区」，忽略了 M1 已有的字符检索本身就是离散判据。

### 5.3 L3 的已知缺陷（必须写明，不许藏）

**M1 实测数据（`tools/probe_retrieval.mjs`，16 条）**：

| 组 | 语义 | 准确率 | 说明 |
|---|---|---|---|
| A 真紧急 | 正在出事 | **4 / 4** | 关键词命中强，这一组可靠 |
| B 预防咨询 | 问知识 | **0 / 4** | 「怎么预防煤气泄漏」→ 误切紧急 |
| C 含词无关 | 不归我管 | **1 / 7** | 「电梯广告怎么投诉」→ 进电梯困人 |
| **合计** | | **31.3%** | |

**因此 L3 的定位必须说清楚**：

| 项 | 定位 |
|---|---|
| 能力 | **能用，但不聪明**。库内场景能找对（M1 实测库内命中 20/20），语义辨析会错 |
| 与 L1 的差距 | **不是精度略低，是维度缺失**——L3 没有意图维度，会把「怎么预防」当「正在出事」 |
| 是否可接受 | **可接受**。因为 L3 只在模型彻底起不来时启用，此时「有 31% 的判断」优于「完全没法用」 |

### 5.4 L3 必须告知用户（不许静默降级）

**静默降级的后果**：用户以为得到的是完整能力，实际是精度最低的一层。

**硬要求**：

| # | 要求 |
|---|---|
| 1 | 顶部常驻提示条：「**当前为基础模式，语义检索不可用**」 |
| 2 | 提示条**不可手动关闭**（与 S8 紧急色带同理，不许用户隐藏自己的能力缺失信息） |
| 3 | 模型加载失败时，在控制台与内置日志中记录失败原因（`unavailable_reason`），供 M3 排查 |
| 4 | **不得因此降级安全规则**：S1（不许编）、S3（`never` 非空）、S5（拨号按钮）在 L3 下全部照旧生效 |

**与 `01` §6.2 的一致性**：Android 离线 TTS 不可用时要求「明确告知并引导安装语音包，不允许静默失败」。L3 遵循同一条原则。

### 5.5 降级边界的实现方式

```js
// 启动时探测一次，结果缓存，不在每次查询时重试
const engine = await probeEngine();
// engine = { embedding: 'ok' | 'failed', reranker: 'ok' | 'failed' | 'offline' }

function pickLayer(engine, online) {
  if (engine.embedding === 'failed') return 'L3';        // 模型级故障，最高优先级
  if (!online || engine.reranker !== 'ok') return 'L2';  // 无精排
  return 'L1';
}
```

**四条实现约束**：

| # | 约束 | 理由 |
|---|---|---|
| 1 | **embedding 失败优先级最高**，不因联网而升到 L1/L2 | 没有向量就没有混合检索，联网也没用 |
| 2 | **探测只在启动时做一次**，不在每次查询重试 | 每次重试会让首次查询多等 1–3 秒；模型坏了不会自己好 |
| 3 | **精排失败按 L2 处理，不降到 L3** | 精排是云端调用，失败通常是网络问题，embedding 仍然可用 |
| 4 | **降级不持久化**，下次启动重新探测 | 用户可能重装了模型文件，不该被上次的失败状态锁死 |

### 5.6 与「未发布场景」的组合

| 情况 | 输出 |
|---|---|
| 任一层命中未发布场景（如「着火了」，`fire_home` 无条目） | **拨号卡**（M1 已有 `renderDialOnly`），不给步骤 |
| 任一层零命中 | 日常 → 拒答；紧急 → 拨号卡（见 §3.5.5） |

> 与 `01` §6.2 一致：离线不做 ASR，用户点图标直接出步骤卡。

| **B1** | **「孩子被热水烫起泡了」完全没识别** | E030 期望 `dialonly`，实际 `refuse`——孩子烫伤时系统回「我答不了」 | `scald_burn` 词表补 5 个：`热水烫`/`烫起泡`/`烫出泡`/`被烫`/`烫红`。**不加单字「烫」**——会让「麻辣烫怎么做」「烫头发」误命中急救 |
| **B2** | **「好像煤气中毒了」判成燃气泄漏** | E027 期望 `co_poisoning`，实际 `gas_leak` | **把 `co_poisoning` 整条规则移到 `gas_leak` 之前**。已验证「煤气漏了」「闻到煤气味」「天然气泄漏」不含 `co_poisoning` 任何词，前移不误伤 |

> **提案与实际实现的偏差（记录在案）**：原提案 B2 写的是「只把『煤气中毒』这个具体词从 `gas_leak` 里摘掉」，但 `gas_leak` 的词表里是「煤气」，**并没有「煤气中毒」这一项**——提案描述有误，无法按字面执行。改为调整规则顺序（即原提案的 A 方案）。已实测确认前移安全。

**为什么要修 B2**：中毒（`120`、搬离+通风）与泄漏（`119`、关阀+撤离）处置路径相反。判错场景会给出**错误方向的建议**，比不给建议更危险。

### 6.5 剩下 40% 误纳率不修，理由写在这里

**④ 库外误纳率 40%（12/30）是 L3 的固有上限，不再靠加规则修。**

典型残留错例：

| 输入 | 期望 | 实际 | 为什么不能靠加词解决 |
|---|---|---|---|
| 「燃气灶打不着火」 | 拒答 | `gas_leak` | 它**真的含「燃气」**。要排除只能加「打不着」这类否定组合，而同类说法无穷（打不燃、点不着、没反应……） |
| 「电梯广告怎么投诉」 | 拒答 | `elevator_trapped` | **真的含「电梯」**。排除「广告/投诉」后，下一步还有「电梯维修电话」「电梯卡在哪办」 |
| 「摔倒保险怎么理赔」 | 拒答 | `fall_elderly` | **真的含「摔倒」** |

**三条的共同点**：场景词真实存在，只是用户问的不是急救。**这是意图问题，不是词表问题。** 加规则等于用穷举对抗开放语义，永远补不完——这正是「字符匹配很不灵活」的具体表现。

**处理方式**：

| 项 | 决定 |
|---|---|
| L3 的 ④ = 40% | **接受**，作为已知上限记入文档。L3 只在模型全挂时启用，此时 60% 正确率优于完全不可用 |
| L1 的 ④ 门槛 | **仍为 0**，由 LLM 意图判定达成，不许因 L3 的现状而放宽 |
| 是否继续给 L3 加词 | **否**。B1 只补了 5 个同类词（烫伤域内闭合），不新增跨域规则 |

### 6.6 三引擎对照实验（2026-11-18）

**背景**：检索逻辑已从 `app.js` 抽到 `app/retrieval.js`（依据 §7.1 D-3），三个引擎都能被同一份 `cases.json` 调用。`--engine=l3|bm25|hybrid` 均可跑。

#### 6.6.1 第一轮：3 条条目（**已作废，保留作方法论记录**）

| 指标 | l3 | bm25 | hybrid |
|---|---|---|---|
| ① 意图准确率 | 60.0% | 60.0% | 60.0% |
| ② 场景准确率 | 79.0% | 79.0% | 79.0% |
| ③ 紧急漏给步骤率 | 0.0% ✓ | 0.0% ✓ | 0.0% ✓ |
| ④ 库外误纳率 | 40.0% | 40.0% | 40.0% |
| ⑤ Hit@3 | 10.0%（1/10） | 10.0%（1/10） | 10.0%（1/10） |
| 综合 action 准确率 | 66.0% | 66.0% | 66.0% |

**三个引擎指标逐项相同。这不是 bug，是三件事实的必然结果**：

| # | 原因 | 证据 |
|---|---|---|
| 1 | **90/100 的样本根本不走检索层** | 危险信号命中时场景由 `DANGER_RULES` 决定，检索层不参与。只有 10 条样本真正考验检索排序 |
| 2 | **意图判定三层共用同一份规则** | 三个引擎只换「无危险信号时的场景检索」，不换 `detectDanger`。所以 ①②③④ 必然相同 |
| 3 | **3 条条目下 BM25 的 IDF 完全失效** | 索引统计：`N=3`、`avgdl=26.7`、45 个词项、**df=1 占比 100.0%**。所有词项的 IDF 相同 → BM25 退化为加权词频匹配，不再有「稀有词权重更高」的能力 |

**第 3 条是本轮最重要的实测发现。** BM25 的核心价值在 IDF 区分度，而 N=3 时 `log(1+(N-df+0.5)/(df+0.5))` 对每个词都算出同一个值。**这意味着现在的 BM25 不是 BM25，是带长度归一化的词频计分。**

**引擎功能本身已验证可用**（排序逻辑正确，只是样本不足）：

```
「被困电梯和摔倒」→ 两个候选
  bm25 : elevator_trapped:4.00 > fall_elderly:1.56
  l3   : elevator_trapped:10   > fall_elderly:5
  hybrid: elevator_trapped:0.0328(l3+bm25) > fall_elderly:0.0323(l3+bm25)
```

三引擎排序一致。但 3 条条目里最多同时命中 2 条，**排序能力的样本宽度不够，无法暴露引擎差异**。

**结论与触发条件**：

| 项 | 状态 |
|---|---|
| 引擎管道 | ✅ 已通，可随时切换与对照 |
| 引擎优劣结论 | ❌ **不能下**。当前数据无法区分三者的检索质量 |
| 重新对照的触发条件 | **published 条目 ≥ 10 条**。届时 `df=1` 占比会显著下降，IDF 恢复区分度，引擎差异才会显现 |
| 在此之前能不能宣称「BM25 更好」 | **不能。** 三个引擎跑出同一个数，任何「某引擎更优」的说法都是编的 |

> **这条实验的价值在于排除了一种错误做法**：如果只看「指标相同」就宣布「BM25 无收益，砍掉」，那是拿样本不足当结论。真原因是知识库只有 3 条，不是 BM25 无用。

#### 6.6.2 第二轮：9 条条目（新增 6 条已发布后）

**先修了一个真实回归**：`fire_home` 发布后，「汽车打不着火」立刻被误判成火灾。根因是**同一个词表在两条路径上检查不一致**——`detectDanger` 有否定前缀检查（`hitNoNegation`），`rankByRules` 没有。条目不存在时这条走不到，条目一发布就暴露。

| 项 | 内容 |
|---|---|
| 现象 | `l3 检索 = fire_home`，`why = keyword*1`；而 `detectDanger = null` |
| 根因 | `scoreEntryByRules` 的 alias/name/keyword 三处正向匹配用了裸 `indexOf` |
| 修复 | 三处全改走 `hitNoNegation`；反向包含（`a.indexOf(t)`）不检查，因为它表示「用户输入更短」，无否定语义 |
| 回归断言 | 自测「库外拒答 20/20」会把这条挡住。**投毒验证**：把 keyword 那行改回裸 `indexOf` → 19/20 变红 |

**同轮还修了测试自身的两个缺陷**：① 注入结构不全的条目会让脚本崩溃而不是报失败（崩溃会掩盖真正原因，等于断言失效），已加防御分支；②「N=3 时 df 全为 1」这条断言硬编码了条目数，每次加条目都误报，已改为断言「索引文档数 == 条目数」+ 打印 df 占比。

**实测（9 条条目，重标后的 100 条集）**：

| 指标 | l3 | bm25 | hybrid |
|---|---|---|---|
| ① 意图准确率 | **61.0%** | 63.0% | 63.0% |
| ② 场景准确率 | 80.0% | 80.0% | 80.0% |
| ③ 紧急漏给步骤率 | 0.0% ✓ | 0.0% ✓ | 0.0% ✓ |
| ④ 库外误纳率 | **40.0%** | 43.3% | 43.3% |
| ⑤ Hit@3 | **20.0%（2/10）** | 30.0%（3/10） | 30.0%（3/10） |
| 综合 action 准确率 | **65.0%** | 63.0% | 63.0% |
| 分组 emergency | 40/40 | 40/40 | 40/40 |
| 分组 prevention | 23.3% | 20.0% | 20.0% |
| 分组 off_scope | 60.0% | 56.7% | 56.7% |

**差异终于出现了，但仍在噪音范围内 —— 不能据此选引擎。**

| 观察 | 数据 | 判断 |
|---|---|---|
| BM25 的 Hit@3 更高 | 3/10 vs 2/10 | **一条样本之差 = 10pp**。Hit@3 有效样本只有 10 条（90 条被 `DANGER_RULES` 截走，不经检索），**这个差异没有统计意义** |

| l3 的综合 action 更高 | 65.0% vs 63.0% | 2 条之差 |
| `df=1` 占比 | 100% → **97.8%**（137 词项） | 只有 3 个词项的 df > 1，IDF 仍未真正恢复区分度 |

**本轮最有价值的结论不是引擎对比，而是这句话**：

> **prevention 组 23.3%、④ 库外误纳 40%，换检索引擎完全无效——三个引擎在这两项上几乎是同一个数。**
> 这两个指标由**意图判定**决定，与检索算法无关。所以下一步的投入方向是 LLM 意图判定，不是换更复杂的检索。

这与 §1 的结论一致：M1 的 31.3% 错误「全部来自意图缺失，不是检索不准」。9 条条目之后这个判断依然成立。

|---|---|

| 结论 | **取 0.60**：使安全项归零的最小阈值，代价 1pp |

这正好落实了 §2.2 早已写下的「`confidence` 低于阈值不猜」——之前只是没实现。

**仍然救不了的那条**：P014「灭火器怎么选」LLM 判 off_scope，confidence 高达 0.95。**高置信度判错，阈值无从下手**，只能靠改 prompt 或补样本。这条记入 T17。

## 8. 运行日志（M0，2026-11-19）

**目的不是「有日志」，而是让「界面什么也没发生」这类故障能被一句话查清。**
起因是 2026-11-18 那次「打字提问不自动朗读」：症状是**什么都没发生**，
而语音失败按设计是静默的（自动读失败不弹提示），于是「没触发」与「被浏览器拦了」
在界面上长得一模一样。最后是靠读代码猜出来的。日志要消灭的正是这种「靠猜」。

### 8.1 六个模块与各自记什么

划分依据是「一次提问会经过谁」，不是按文件切。M0 是底座，其余五个是业务模块。

| # | 模块 | `module` 值 | 关键打点 | 级别 |
|---|---|---|---|---|
| M0 | 日志底座 `app/log.js` | — | 自身失败（`sendFail`/`noTransport`/`dropped`） | — |
| M1 | 知识库加载 | `knowledge` | slots/entries/data_date/generated_at/slotIds | **always**（启动 1 行） |
| M2 | 检索 `app/retrieval.js` | `retrieval` | 危险信号命中词、各条规则分、候选、最终 `entryId/score/why/候选数` | 摘要 always；明细 debug |
| M3 | 意图判定 `app/llm.js` + `tools/llm_proxy.mjs` | `llm` / `proxy` | 耗时、`intent/scene/confidence`、`belowThreshold`、`action`+`reason` | 摘要 always；超时/失败 **warn** |
| M4 | 语音 `app/voice.js` | `voice` | 探测结果与原因、朗读稿长度与首 20 字、`ok/cancelled/error`、静默位 | 开始朗读 always；失败 **warn** |
| M5 | 路由与渲染 `app/app.js` | `app` | 输入截断、`kind` 落点、`mode/locked`、**自动朗读跳过及原因** | 摘要 always；不读原因 **info** |

### 8.2 三条必须守住的约束（都有断言）

| 约束 | 为什么 | 断言 |
|---|---|---|
| **密钥绝不入日志** | key 泄露不可逆（`01` §8 红线）。前端脱一次，代理收到**再脱一次**，不信前端自觉 | `scrubString` 对 `sk-`/`Bearer`/`api_key=` 三类均替换；字段名为 `api_key/token/secret` 的整条替换 |
| **日志不能改变产品行为** | 日志挂了不能白屏 | console 抛错时 `emit` 不向上抛 |
| **提问原文只记前 40 字** | 那是老人说的话，本地可留但不许全文堆积 | `clipText` 截断并标注原字数 |

### 8.3 级别策略：默认 WARN+，但「每模块一条摘要」强制落盘

这块是个取舍，写清楚免得后人以为是 bug：

- 默认阈值 `warn`，关闭全部 info/debug → 正常运行**一行都不落盘**。
- 但那样「各模块都有日志」就是空话。所以留一个受控例外 `LOG.always()`：
  **每次提问，每个模块只写 1 行摘要**，绕过级别筛选。
- 明细（逐条得分、候选清单、每个 debug 事件）要 `?log=debug` 才写。

一次提问落盘约 4–6 行，能读出「命中什么 → 判成什么 → 给了什么卡 → 读没读」。
要更细就带 `?log=debug` 复现一次。

### 8.4 traceId：一次提问一根线

入口（`handleQuery` / `handleIconClick` / 单独调同步路径）生成 `q-xxxx-N` / `i-xxxx-N`，
**五个模块的每行日志都带同一个 trace**。没有它就只能靠时间戳对齐，
而 LLM 是异步的（1 秒延迟 + 超时分支），时间戳对不准。

一次真实提问在 `logs/app-YYYY-MM-DD.log` 里长这样（2026-11-19 实跑输出）：

```
proxy     judge 完成  {intent:ongoing, scene:gas_leak, confidence:0.98, cached:true, latency_ms:0}
llm       判定完成    {ms:10, intent:ongoing, confidence:0.98, belowThreshold:false}
llm       路由结论    {action:steps, entryId:gas_leak, reason:"llm-ongoing"}
app       路由决策    {path:llm, input:"煤气漏了", kind:steps, mode:emergency, locked:true}
```

### 8.5 落盘与降级

| 环节 | 做法 | 为什么 |
|---|---|---|
| 谁写文件 | 前端 `POST /log` → `tools/llm_proxy.mjs` 追加写 | 浏览器 JS 没有文件写权限，这是唯一零依赖路径 |
| 写不满怎么办 | 攒 20 条或 2 秒 flush 一次；`pagehide` / 切后台时强制 flush | 老人直接关页面，最后几条往往正是出问题那几条 |
| 代理没起 / APK 无代理 | 退化：控制台 + 内存环形缓冲（500 条），`noTransport` 计数 | **不许影响产品**；也不许假装写成功 |
| 文件管理 | `logs/app-YYYY-MM-DD.log`，单文件 5MB 切分，保留 7 天 | 日志是排查工具，不是数据资产 |

`logs/` 已在 `.gitignore` 里——日志里有提问原文，不进仓库。

### 8.7 怎么用（四条常用命令）

```bash
node tools/llm_proxy.mjs                     # 起代理（日志落盘靠它）
ls logs/                                     # 当天文件：app-2026-11-19.log

# 看某根 trace 的完整链路（一次提问一行因果）
grep 'q-xxxx' logs/app-*.log

# 只看警告与错误（默认级别下文件里就这些 + 每模块摘要）
grep -E '"level":"(warn|error)"' logs/app-*.log
```

要看明细（逐条得分、候选清单、每个 debug 事件），在页面地址后加 `?log=debug` 再复现一次：
`index.html?log=debug`。切回默认级别只要去掉参数。

### 8.6 「日志里没有」必须能区分两种含义

这是本层最容易被做错的地方：**日志没记录 ≠ 事情没发生**。
所以底座自己也要可观察：`LOG.stats()` 返回 `buffered / pending / dropped /
flushFail / sendFail / noTransport`。`noTransport` 尤其重要——
2026-11-19 实测踩过一次：`flush` 只找 `global.fetch`，而宿主只在顶层有 `fetch`，
结果**日志被静默丢光而 `sendFail` 仍是 0**。现在这条路会计数，不再装成功。
