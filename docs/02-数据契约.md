# 02 · 数据契约

> 版本 v0.5 ｜ 2026-11-18 ｜ 状态：待评审（v0.5 变更见 §12）
> **唯一真源。任何字段增删改，先改本文，再改代码。**
> 本文定义的 `knowledge/*.json` 同时供三条通道消费：日常问答、紧急应答、离线内置包。

## 1. 三条硬约束

| # | 约束 | 违反的后果 | 对应安全规则 |
|---|---|---|---|
| 1 | **步骤必须是数据，不能是整段文案** | 无法校验字数、无法打勾、无法分段播报 | S2 |
| 2 | **`never`（绝对不要做）与步骤同级，不可省** | 多数事故伤亡来自"做了不该做的事" | S3 |
| 3 | **每条必须能回溯来源四要素** | 无法核对 = 无法证明没编 | S2 |

## 2. 文件组织

```
knowledge/
├── index.json              # 【手改】场景注册表 slots（见 §4.1）
├── manifest.json           # 【生成】版本 + 校验和，M3 更新机制用
├── gas_leak.json           # 【手写】一个场景一个文件
├── fire_home.json
├── co_poisoning.json
├── fall_elderly.json
├── scald_burn.json
├── electric_shock.json
├── airway_obstruction.json
├── drowning.json
├── earthquake.json
└── elevator_trapped.json
```

**三条硬规则：**

1. **一个文件 = 一个场景 = 一个 entry 对象。**
   理由：4 人协作，一个文件同一时刻只能有一个写者；合并冲突时以文件为单位回退。
2. **`index.json` 是手改的注册表，不是生成物。** 这是唯一允许手工编辑的"索引"文件。
3. **`_` 和 `.` 开头的文件不参与校验。** 用于临时备份（如 `_bak.json`），校验脚本会打印跳过清单。

## 4. 结构定义（注册表 / 枚举 / 嵌套对象）

### 4.1 `category`：注册表驱动（v0.2 改）

**`category` 的合法值不写在代码里，而是来自 `knowledge/index.json` 的 `slots` 注册表。**

```
knowledge/index.json
  └── slots[]  ← 槽位（slot）：声明「这里会有一个场景」
        ├── id      唯一标识，与 <id>.json 文件名一致
        ├── name    显示名
        ├── icon    图标资源名
        ├── order   排序值，间隔 10，便于插队
        ├── state   "slot"（无内容）| "ready"（有 published 条目）
        ├── show_when_empty  无内容时是否显示灰图标
        └── note    备注（为什么加这个场景、来源查证进度）

knowledge/<id>.json  ← 条目（entry）：实际内容，由 §3 字段定义
```

**槽位与条目的关系**：

| 情况 | 前端 | 校验脚本 |
|---|---|---|
| 有 slot，有 entry 且 `published` | 正常图标 | PASS |
| 有 slot，无 entry | `show_when_empty: true` → 灰图标「内容准备中」；`false` → 隐藏 | PASS（打印提示） |
| 有 slot，有 entry 但未 `published` | 不显示 | PASS（打印提示） |
| **无 slot，有 entry** | 不显示 | **FAIL**（禁止幽灵场景） |
| slot.id 重复 / icon 重复 / order 重复 | — | **FAIL** |

**加场景的操作手册（两步，不改代码）**：

```bash
# 1. index.json 的 slots 里加一行
{ "id": "snake_bite", "name": "蛇咬伤", "icon": "snake_bite",
  "order": 110, "state": "slot", "show_when_empty": false, "note": "待查" }

# 2. 新建 knowledge/snake_bite.json，按 §3 字段填写
# 3. 跑 python tools/validate_knowledge.py 确认 PASS
```

**删场景的操作**：先删 `<id>.json`，再删 slot。**顺序反了脚本会 FAIL**（有 entry 无 slot）。

**候选池（v0.5 更新：3 个已 `ready`，7 个仍 `slot`）**：

| id | 中文 | order | 默认主推号码 | `life_threatening` 倾向 | `state` | 备注 |
|---|---|---|---|---|---|---|
| `gas_leak` | 燃气泄漏 | 10 | 119 | true | **ready** | 已发布 v1.0，机器比对 pass |
| `fire_home` | 家庭火灾 | 20 | 119 | true | slot | 亡人主体在居住场所；**内容尚未写入** |
| `co_poisoning` | 一氧化碳中毒 | 30 | 120 | true | slot | **无味无形，与燃气泄漏是两件事**；注意 `DANGER_RULES` 中须排在 gas_leak 之前（见 `03` §6.3） |
| `fall_elderly` | 老人跌倒 | 40 | 120 | 视情况 | **ready** | 已发布 v1.0；危重分支（意识不清/呕吐）待补 |

### 4.2 `emergency_number`

单值字符串，只能取 `"119"` / `"120"` / `"110"`。

按场景给**一个**主推号码。

> **v0.6 变更**：原「前端另有常驻小字『紧急情况请直接拨 120』，不由本字段控制」一句随 S9 删除。页脚常驻拨号行已移除。
> 本字段的消费者变为两处：**场景卡内的拨号按钮**（依据 `01` §5 S5），以及 M2 的语音播报（「同时拨打 120」）。

### 4.3 `source` 四要素

```json
"source": {
  "name": "应急管理部《家庭消防安全手册》",
  "url": "https://www.mem.gov.cn/...",
  "date": "2026-11-18",
  "quote": "原文照抄的一句，不转述"
}
```

| 子字段 | 约束 |
|---|---|
| `name` | 发布机构 + 文件名，不许只写"网上资料" |
| `url` | 可点击的原始发布页，不许转载页 |
| `date` | 我们获取/核对的日期 |
| `quote` | **必须能逐字比对**。写"概括"的条目审核不通过 |

### 4.4 步骤结构 `steps`（v0.4 改：字符串 → 对象）

**每个步骤是一个对象，不是字符串。**

```json
"steps": {
  "immediate": [
    { "text": "立即关闭燃气总阀", "tool": null },
    { "text": "打开门窗通风", "tool": null },
    { "text": "马上拨打 119", "tool": { "name": "dial", "number": "119" } }
  ],
  "next": [
    { "text": "到室外再打电话", "tool": null }
  ],
  "never": [
    { "text": "不要开灯或按门铃", "tool": null },
    { "text": "不要在室内打电话", "tool": null }
  ]
}
```

| 子字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `text` | string | ✔ | 动词开头，≤ 20 字，一个动作只写一件事 |
| `tool` | object \| null | ✔（可为 null） | 该步骤需要调用的工具，见 §4.5 |

**为什么改成对象**（这是 v0.4 的核心变更）：

1. **工具必须按场景声明，不能由代码猜。** 冲水 20 分钟的计时器只对烧烫伤有意义，对燃气泄漏是干扰。若写死在代码里判断 `if category == ...`，场景逻辑就会在数据和代码里各存在一份，改一处漏一处。
2. **为 M2 的 Agent 化留位。** 状态跟踪、动态分流都要附加在具体步骤上，字符串无处挂载。
3. **M1 无成本。** M1 不执行工具，所有 `tool` 为 `null`，渲染层只取 `text`。

**迁移说明（旧格式会被脚本拒绝）**：

```
"immediate": ["关阀", "开窗"]          ← 旧格式，FAIL
"immediate": [{ "text": "关阀", "tool": null }, ...]   ← 新格式
```

### 4.5 步骤级工具声明 `tool`

**工具不设"通用工具层"，由知识条目按场景自行声明。** 代码只负责执行，不负责判断该调哪个。

| `name` | 参数 | 用途 | 适用场景举例 | **不适用**举例 |
|---|---|---|---|---|
| `dial` | `number`: `"119"`/`"120"`/`"110"` | 唤起拨号盘并预填（**不自动拨出**） | 火灾、燃气泄漏、昏迷 | 电梯困人（先按警铃） |
| `timer` | `seconds`: 正整数，`label`: string | 计时并语音报数 | 烧烫伤冲水 20 分钟、心肺复苏按压节奏 | 燃气泄漏（先撤离，计时无意义） |
| `repeat` | `times`: 正整数 | 重复播报该步骤 | 需要跟读确认的动作 | 单次动作 |

```json
"tool": { "name": "timer", "seconds": 1200, "label": "冷水冲伤口" }
```

**三条硬规则**：

1. **`tool.name` 只能取上表三个值**，越界即 FAIL。扩工具须先改本文。
2. **`tool` 只能挂在 `immediate` 和 `next` 上，`never` 不允许带工具**——禁忌项是"不要做"，挂计时器毫无意义。
3. **`tool` 为 `null` 是常态，不是占位。** 大部分步骤不需要工具；为了"看起来像 Agent"而硬塞工具，是给用户增加干扰。

**M1 / M2 的差异**：

| 里程碑 | 工具行为 |
|---|---|
| M1 | 全部忽略，只渲染 `text`。`tool` 字段只做 schema 校验 |
| M2 | 按声明执行。执行失败时**回落到纯播报**，不许静默失败 |

## 5. 分诊 `triage`

**作用**：同一句「煤气漏了」，有明火和无明火的第一步完全不同。**先问 1 个关键分支，再给步骤。**

```json
"triage": {
  "question": "屋里能看到明火，或者煤气味很浓吗？",
  "options": [
    {
      "value": "flame",
      "label": "有明火 / 味很浓",
      "override": {
        "immediate": [
          { "text": "立刻撤离到室外", "tool": null },
          { "text": "到室外拨打 119", "tool": { "name": "dial", "number": "119" } }
        ]
      }
    },
    {
      "value": "no_flame",
      "label": "没有明火",
      "override": null
    }
  ]
}
```

| 规则 | 说明 |
|---|---|
| 问题数 | **只能 1 个**。多问题会拖死老人 |
| 选项数 | 2–3 个，不得超过 |
| `override: null` | 该分支使用默认 `steps` |
| `override.immediate` | 非 null 时至少 2 条、最多 7 条；**元素结构同 §4.4 的步骤对象**，同样受 20 字限制 |
| `triage: null` | 表示该场景无关键分支，直接用默认步骤 |

> **v0.4 提示**：`override.immediate` 的元素也必须是 `{text, tool}` 对象，不接受纯字符串。

## 6. 日常模式 `daily`

```json
"daily": {
  "summary": "燃气泄漏指管道、软管、灶具漏气，遇明火或电火花可能爆炸。",
  "why": "燃气比空气轻或重，会在低处或高处聚集……（≤150字，讲原理）",
  "prevention": ["每年检查一次软管", "装燃气报警器"],
  "misconception": "闻到味道先开抽油烟机——错，抽油烟机会产生电火花。"
}
```

| 子字段 | 约束 | 说明 |
|---|---|---|
| `summary` | ≤ 60 字，必填 | 一句话是什么 |
| `why` | ≤ 150 字，必填 | 为什么这样做（LLM 可基于此扩写） |
| `prevention` | 1–5 条，每条 ≤ 25 字，必填 | 日常预防 |
| `misconception` | ≤ 80 字，可为 null | 常见误区，**优先级最高的内容** |

**日常模式的 LLM 边界（S7）**：允许基于 `why`/`prevention` 扩写解释，但**任何操作动作必须来自 `steps` 或 `never`**。

## 7. 审核状态机

### 7.1 状态与流转

```
draft ──提交──> pending_review ──审核通过──> approved ──发布──> published
                    │                                            │
                 驳回│                                        下架│
                    ↓                                            ↓
                  draft                                       archived
```

| 状态 | 含义 | 是否可上线 |
|---|---|---|
| `draft` | 编写中 | ✗ |
| `pending_review` | 待审 | ✗ |
| `approved` | 审核通过，待发布 | ✗ |
| `published` | 已上线 | ✔ |
| `rejected` | 驳回，附理由 | ✗ |
| `archived` | 已下架 | ✗ |

**禁止的流转**：
- `draft` → `published`（跳过审核）
- `published` → `draft`（线上内容不许直接改，必须新建版本）
- ~~任何状态 → 自审自过~~（**v0.3 已解禁**：允许编写者自行审核，见 §7.2）

### 7.2 `review` 结构（v0.4：加机器比对层）

```json
"review": {
  "author": "A",
  "approved_by": ["A"],
  "approved_at": "2026-11-20",
  "checklist": {
    "step_order_ok": true,
    "never_non_empty": true,
    "source_quote_verbatim": true
  },
  "agent_check": {
    "source_quote": "pass",
    "checked_at": "2026-11-20",
    "detail": "已在原文中定位到 quote，起始于第 3 段"
  },
  "reject_reason": null
}
```

**审核只审三项**（不做文字润色评审），但三项的**判断主体不同**：

| 检查项 | 判据 | **谁来判** | 不通过示例 |
|---|---|---|---|
| `step_order_ok` | 步骤顺序无误，无"先做后做"颠倒 | **人** | 燃气泄漏把"开灯查看"放在"关阀"前 |
| `never_non_empty` | 禁忌项 ≥ 1 条且是本场景真实风险 | **人** | 写"注意安全"这种空话 |
| `source_quote_verbatim` | `quote` 能在原文中**逐字找到** | **机器**（`agent_check`） | 把两句话概括成一句 |

**为什么 `source_quote_verbatim` 必须由机器判**：人肉眼比对上百字必漏，机器不会。这一项是「不许编」能否被证明的唯一依据，不能只靠人点勾。

#### `agent_check.source_quote` 三态

| 值 | 含义 | 能否 `published` |
|---|---|---|
| `pass` | 已在原文中逐字定位到 `quote` | ✔ 可 |
| `fail` | 抓到了原文，但找不到该句（或只有近似） | ✗ 禁止 |
| `unverified` | **没抓到原文**（网络失败 / 页面改版 / 需登录 / PDF 无法解析） | ✗ 禁止，转人工 |

**硬规则：`unverified` 不等于 `pass`。** 抓不到就如实标 `unverified`，交人工处理。**把"没查出问题"当成"没问题"是本项目最危险的错误。**

**由 `tools/check_source_quote.py` 生成**，人工不得手填 `pass`。

#### 验证人数

`approved_by` 长度 ≥ 1（v0.3 裁决：单人验证，允许自审）。

**保留的约束（不因人数减少而放宽）**：

- `checklist` 三项仍须全为 `true` 才能 `published`，缺一即 FAIL。
- `draft` → `published` 仍禁止直接跳转，必须经过 `pending_review`。
- `source_quote_verbatim` 现在由**机器**判定（`agent_check`），人的这一票不再单独成立。
- `status: published` 时，`agent_check.source_quote` 必须为 `pass`，`unverified` 与 `fail` 一律拒绝发布。

### 7.3 `status` 与上线的硬关系

- 前端与离线包**只允许加载 `status: "published"` 的条目**。
- 构建脚本遇到非 `published` 条目必须**跳过并打印警告**，不得静默包含。
- 离线包内置的是发布时的 `published` 快照，升级靠整包替换。

## 8. 版本与更新（M3）

### 8.1 两级版本

| 字段 | 位置 | 含义 | 何时升 |
|---|---|---|---|
| `schema_version` | 每个文件 | **结构**版本 | 字段增删改时 |
| `version` | 每个 entry | **内容**版本 | 该条目内容改动时 |
| `manifest.version` | `manifest.json` | **整包**版本 | 任一条目重新发布时 |
| `manifest.data_date` | `manifest.json` | **数据日期**，界面显示用 | 同上 |

### 8.2 `manifest.json`

```json
{
  "schema_version": "1.0",
  "version": "2026.11.20.1",
  "data_date": "2026-11-20",
  "entry_count": 8,
  "checksum": "sha256:...",
  "files": ["gas_leak.json", "fire_home.json"]
}
```

### 8.3 更新流程

```
启动 → 读本地 manifest → （有网时）拉远端 manifest
   ├─ 版本相同 → 不更新，显示 data_date
   ├─ 版本不同 → 下载整包 → 校验 checksum
   │        ├─ 校验通过 → 替换 → 重启生效
   │        └─ 校验失败 → 保留旧版本，提示更新失败（不静默）
   └─ 无网 → 用内置版本，顶部显示「当前离线 · 数据版本 YYYY-MM-DD」
```

**三条硬规则**：
1. **整包替换，不做增量补丁**（全部场景约 20–30KB，补丁只增加复杂度）。
2. **校验失败必须回滚**，不得让半损坏的数据上线。
3. **旧版本也要显示数据日期**，不许隐藏。

## 9. 非法值清单（写入时必须拦截）

| 非法情况 | 拦截方式 |
|---|---|
| `steps.*` 任一为空数组 | schema 校验拒绝 |
| **步骤写成字符串（旧格式），不是 `{text, tool}` 对象** | **拒绝，并提示迁移到 §4.4** |
| **步骤对象缺 `text`，或 `text` 为空** | 拒绝 |
| 任一步骤 `text` > 20 字 | 脚本统计字符数（中文按字计） |
| **`tool.name` 不在 `dial` / `timer` / `repeat` 内** | 拒绝（扩工具须先改本文） |
| **`tool.name = "timer"` 但缺 `seconds` 或 `seconds` ≤ 0** | 拒绝 |
| **`tool.name = "dial"` 但 `number` 不在 119/120/110** | 拒绝 |
| **`never` 段落挂了 `tool`** | 拒绝（禁忌项不得带工具） |
| `never` 缺失或为空 | S3 判据，拒绝入库 |
| `source.quote` 少于 10 字 | 视为概括，拒绝 |
| **`status: published` 但 `agent_check.source_quote` 不是 `pass`** | **拒绝发布（`unverified` 也不行）** |
| **`agent_check` 缺失或 `checked_at` 为空** | 拒绝发布 |
| `category` 不在 `index.json` 的 `slots` 内 | 拒绝（先在注册表加 slot） |
| `category` 与 `id` 不一致 | 拒绝 |
| 有 entry 但注册表无对应 slot | 拒绝（幽灵场景） |
| slot 的 `id` / `icon` / `order` 重复 | 拒绝 |
| slot 的 `state` 不是 `slot` / `ready` | 拒绝 |
| `status: published` 但 `approved_by` 为空（0 人） | 拒绝发布 |
| `status: published` 但 `checklist` 未全 `true` | 拒绝发布 |
| `id` 与文件名不一致 | 拒绝 |
| `triage.options` 超过 3 个 | 拒绝 |
| 步骤中含多个动作挤在一句（如"关阀并开窗"） | **建议拆分**，审核项 |

> 该条目现已 `published`，若示例继续跟随真实文件，**照抄的人会直接带上 `published` 跳过审核**——这违反 §7.1 的禁止流转（`draft` → `published` 不许直跳）。

**关于这个模板的四个要点：**

### v0.4（2026-11-18）

**步骤结构对象化 + 步骤级工具声明 + 机器比对层（用户裁决：单人 + 机器强制比对）**

| 变更 | v0.3 | v0.4 |

**新增文件**：`tools/check_source_quote.py` —— 抓 URL 逐字比对 `quote`，输出 `pass` / `fail` / `unverified`。

**为什么加机器比对**：`source_quote_verbatim` 是「不许编」能否被证明的唯一依据。人肉眼比对上百字必漏，机器不会。**审核人数从 2 减到 1 省下的人力，由机器在这一项补回来。**

**核心原则（写死，不许绕过）**：
> **`unverified` ≠ `pass`。** 抓不到原文就如实标 `unverified`，转人工。把"没查出问题"当成"没问题"，是本项目最危险的错误。

**迁移影响**：现有 `knowledge/elevator_trapped.json` 已迁移到新结构。旧格式条目会被 `validate_knowledge.py` 拒绝并提示迁移。
